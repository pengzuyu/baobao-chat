# BaobaoChat 内网部署操作手册（v0.1.5）

> 交付物：`baobaochat-deploy-v0.1.5.tar.gz`（compose 单机）与 `baobaochat-k8s-v0.1.5.tar.gz`（K8s）。
> 一次上线分两段：**① 服务端跑起来 → ② 客户端发下去**。全文以 Linux + 内网裸 HTTP 为准。
> 占位符：`<SERVER_IP>` = 服务器/节点内网 IP；`<ver>` = 版本号（本次 0.1.1 / 服务端 0.1.5）。

---

## 0. 开工前必须确认的一件事：地址契约

客户端在**编译期**把服务端地址写死成三条链（API `/api/v1`、WS `/ws`、更新源 `/update/latest.json`），
安装后无法在客户端里改。因此：

> **部署地址必须与 Windows 客户端出包时的 `BBC_PUBLIC_URL` 完全一致**
> （协议、IP/域名、端口、有无尾斜杠都要一致）。

| 形态 | 客户端出包时应使用的地址 | 服务端对应配置 |
|---|---|---|
| compose 单机（80 端口） | `http://<SERVER_IP>` | `.env` 的 `BBC_PUBLIC_DOMAIN=<SERVER_IP>` |
| K8s（NodePort 30808） | `http://<NODE_IP>:30808` | values 的 `global.domain=<NODE_IP>:30808` |

**核对出包地址的三种办法**（任选其一，务必落实）：

1. 查 GitHub Actions `Windows 客户端包` 那次运行的 `public_url` 输入；
2. 问出包执行人 / 查构建命令历史（`BBC_PUBLIC_URL=... powershell build-desktop.ps1`）；
3. 装到一台 Windows 后登录，用资源监视器看客户端进程连接的远端 IP:端口，反推地址。

> 若地址已写死且与本次部署地址不一致：**只能重出客户端包**（改服务端地址无效）。
> 80 端口被占用需要改成其他端口时，客户端地址要带端口，同样需要重出包。

## 1. 选形态

| 场景 | 用哪个包 |
|---|---|
| 单台虚拟机 / 内网小规模（≤2k 用户）/ 无自愈要求 | **compose 包（第 2 章，推荐起步）** |
| 已有 K8s 集群 / 多租户 / 要自愈与灰度 | **K8s 包（第 3 章）** |

两种形态能力完全等价（聊天/文件/知识库/Agent/客户端发布全部具备），数据也可平移。

## 2. compose 单机部署（主线）

### 2.1 上传、解包、校验

```bash
# 把 tar.gz 传到服务器（scp / 内网文件共享均可）
sha256sum -c baobaochat-deploy-v0.1.5.tar.gz.sha256 2>/dev/null || true   # 若随包给校验值
tar xzf baobaochat-deploy-v0.1.5.tar.gz
cd baobaochat-deploy-v0.1.5
sha256sum -c SHA256SUMS | tail -3          # 期望全部 OK
```

包内结构：

```
INSTALL.md                 本包的简版说明
SHA256SUMS                 全文件校验
gen-oidc-key.sh            OIDC 启用时才用（第 6 章）
images/bbc-app-0.1.5.tar.gz   服务端镜像
images/base-images.tar.gz     5 个第三方镜像（pgvector/nginx/redis/rustfs/aws-cli）
compose/                  docker-compose.yml + .env.internal + 脚本 + volumes/
```

### 2.2 载入镜像

```bash
docker load -i images/bbc-app-0.1.5.tar.gz
docker load -i images/base-images.tar.gz
docker images | grep -E "bbc-app|pgvector|rustfs|aws-cli|nginx|redis"   # 确认都在
```

> Docker 前置：Engine ≥ 24 + Compose v2.20（`docker compose version`）。
> 单机全量离线包不需要私服 / registry-mirrors。

### 2.3 配置 `.env`（三处必改）

```bash
cp compose/.env.internal compose/.env
vi compose/.env
```

| 键 | 必须改成 | 为什么 |
|---|---|---|
| `BBC_PUBLIC_DOMAIN` | `<SERVER_IP>`（不带 `http://`、不带路径） | 服务端对外基址；更新清单 URL 也由它推导 |
| `BBC_S3_PUBLIC_ENDPOINT` | `http://<SERVER_IP>/oss` | 文件上传走预签名直传。**留空=签名出容器内地址 `http://rustfs:9000`，客户端不可达 → 头像/文件/客户端发布上传全部失败** |
| `POSTGRES_PASSWORD` + `BBC_DB_DSN` | 建议沿用随机值；要改必须两处同步 | 两处不一致 = app 连不上库 |

其余凭据（`BBC_JWT_SECRET` / `BBC_S3_ACCESS_KEY` / `BBC_S3_SECRET_KEY` / `BBC_KMS_MASTER_KEY`）
已随机生成，**建议原样保留**。其中 `BBC_KMS_MASTER_KEY` 是 AI 供应商 API Key 的信封加密主密钥，
**删掉/换掉 = 已录入的供应商密钥全部解不开**。

> 证书：`compose/volumes/certs/` 已随包带一套自签证书（nginx 443 段要求文件存在，否则容器启动即失败）。
> v0.1 客户端走 **http 80**，可不管它；将来切 https 时用内部 CA 签发的 `tls.crt`/`tls.key`/`ca.crt`
> 同名覆盖后 `docker compose up -d nginx-lb` 即可。

### 2.4 起服

```bash
cd compose
docker compose --profile core up -d
docker compose ps          # 期望：app/pg/redis/rustfs/nginx-lb/update-src/website running(healthy)
```

首次启动会：

1. `rustfs-init` 建三个桶：`bbc-data`（版本化）、`bbc-backup`、`bbc-releases`（客户端安装包，匿名只读）；
2. `app` 启动时自动应用 schema 迁移（62 张表，约 30–60 秒）；
3. `app-init` 只负责等 pg 就绪（跑完即 `exited(0)`，属正常）。

```bash
docker compose logs app-init | tail -5      # 看到「数据库初始化完成」
docker compose logs app | grep -iE "migrat|listen|ready" | tail -10
```

### 2.5 健康校验

```bash
curl -s http://<SERVER_IP>/healthz                          # → ok
curl -s http://<SERVER_IP>/api/v1/setup/status               # → {"need_setup":true,...}
curl -s -o /dev/null -w '%{http_code}\n' http://<SERVER_IP>/update/latest.json
#   → 404 属正常（尚未发布客户端，第 4 章发布后变 200）
```

### 2.6 创建首超管

浏览器打开 `http://<SERVER_IP>/` → 自动跳 `/setup` 向导 → 填管理员账号/姓名/口令 →
完成并自动登录。**向导只在系统无任何用户时出现，建户即永久关闭。**

### 2.7 配 AI 供应商（Agent 功能的前置）

管理后台 → **AI 供应商** → 新增（如智谱 GLM）：

1. 填供应商名称、Base URL（如 `https://open.bigmodel.cn/api/paas/v4`）与 API Key；
2. 在「模型」处登记要用的模型名（如 `glm-4.7-flash`），并设为默认路由；
3. 保存后到聊天/工作台发一条消息验证 Agent 有响应。

> Key 由 `BBC_KMS_MASTER_KEY` 信封加密存库；管理台只回显掩码。
> 供应商没配好时，IM/文件等功能正常，只是 Agent 不可用。

### 2.8 冒烟（5 分钟）

- [ ] 两个账号互发消息（可用管理后台「组织用户」建第二人）
- [ ] 传一张图片、下载回来（验证对象存储与预签名）
- [ ] 知识库新建一篇笔记
- [ ] 工作台发一句「你好」→ Agent 有回复（验证供应商与 KMS）
- [ ] 管理后台 → 审计，能看到刚才的操作

## 3. K8s 部署（对照版）

完整分步见包内 `INSTALL-K8S.md`（8 步）。这里只列与 compose 的**差异点与坑**：

| 项 | K8s 形态 |
|---|---|
| 唯一入口 | `bbc-web` Service **NodePort 30808**（官网 + 更新源 + `/api` `/ws` `/oss` 分流） |
| 对象存储直连 | RustFS NodePort **30900**；values 的 `externalServices.s3.publicEndpoint` 必须是 `http://<NODE_IP>:30900` |
| 地址替换 | `values-k8s.example.yaml` 里两处 `<NODE_IP>`（`global.domain` 与 `s3.publicEndpoint`）必须替换为同一节点 IP |
| 镜像 | 先 `docker load` 再推私服 8182（app + web + 3 个依赖镜像）；`deps/web.yaml` 的 `__IMAGE__` 用 sed 替换 |
| 迁移 | helm hook job 自动跑（`kubectl wait --for=condition=complete job -l app.kubernetes.io/component=migrate`） |
| 入口镜像更新 | `kubectl -n baobao-chat set image deploy/bbc-web web=<私服>/web:<ver>`（Recreate 策略，短暂中断） |

```bash
# 关键命令顺序（详见 INSTALL-K8S.md）
kubectl apply -f deps/namespace.yaml
kubectl -n baobao-chat create secret generic bbc-pg-cred  --from-literal=password='<values 里的 PG 密码>'
kubectl -n baobao-chat create secret generic bbc-s3-cred  --from-literal=accessKey='...' --from-literal=secretKey='...'
kubectl apply -f deps/postgres.yaml && kubectl apply -f deps/rustfs.yaml
kubectl apply -f deps/rustfs-init.yaml      # 建三桶（含 bbc-releases）
helm install bbc chart/bbc-0.1.0.tgz -n baobao-chat -f values-k8s.example.yaml
sed "s|__IMAGE__|<私服>/web:0.1.5|" deps/web.yaml | kubectl apply -f -
curl -s http://<NODE_IP>:30808/healthz      # → ok
```

> 客户端出包地址固定为 `http://<NODE_IP>:30808`；改节点 IP 也要重出客户端包。

## 4. 客户端分发（Windows，D39 管理后台）

### 4.1 补签（CI 出的 Windows 包是未签名包）

自动更新要求安装包旁有 minisign `.sig`（与客户端内置 pubkey 配对）。在 **mac 构建机**上执行：

```bash
cd /Users/pengzuyu/Documents/trae_projects/baobao-work

# 口令取自 ~/.tauri/bbc-updater.env（变量 BBC_UPDATER_PASSWORD）
export TAURI_SIGNING_PRIVATE_KEY_PASSWORD="$(sed -n 's/^BBC_UPDATER_PASSWORD=//p' ~/.tauri/bbc-updater.env)"

cd client
npx tauri signer sign -f ~/.tauri/bbc-updater.key \
  -p "$TAURI_SIGNING_PRIVATE_KEY_PASSWORD" \
  ../out/release/v0.1.1/windows-x86_64/BaobaoChat_0.1.1_x64-setup.exe
# 产出：同目录 BaobaoChat_0.1.1_x64-setup.exe.sig
```

> 若 Windows 包是本地 `build-desktop.ps1` 带私钥出的，则已自带 `.sig`，跳过此步。
> `.sig` 与平台无关，只与 updater 私钥配对——mac 包用的同一把私钥即可给 Windows 包签。

### 4.2 上传并发布

1. 管理员登录 → 管理后台 → **客户端发布**
2. 右上「上传」：版本 `0.1.1`、平台 `Windows（NSIS）`、选 `BaobaoChat_0.1.1_x64-setup.exe`、
   把 `.sig` 文件内容整段粘进「签名」
3. 提交后是**草稿**；勾选该版本 → **发布**（整版本发布：同版本所有草稿一起转正）
4. 若同版本也有 mac 包，一并上传后再发布（保证该版本各平台齐全）

> 发布语义：整版本发布；**回滚**把目标版本的发布时间提到最新（清单指针回退，不挪文件）；
> **撤回**从清单与历史移除（已装用户不受影响）。
> 同一版本同一平台不可覆盖（制品不可变）；要重传请升版本号。

### 4.3 分发验证清单

```bash
curl -s http://<SERVER_IP>/update/latest.json | head -c 400
#   期望 platforms.windows-x86_64.url 指向 http://<SERVER_IP>/update/releases/v0.1.1/windows-x86_64/...
curl -s http://<SERVER_IP>/update/release-info.json | head -c 300
#   期望 downloads 含 Windows 条目
curl -sI http://<SERVER_IP>/update/releases/v0.1.1/windows-x86_64/BaobaoChat_0.1.1_x64-setup.exe | head -3
#   期望 200（对象存储直出）
```

- [ ] 浏览器打开官网 `http://<SERVER_IP>/`，下载区出现 **Windows** 下载按钮，能下载
- [ ] Windows 上装包 → 用管理员分配的账号登录（握手成功=地址契约正确）
- [ ] 已装旧版（0.1.0）的机器：设置 → 关于 → 软件更新 → **检查更新** → 出现 0.1.1 → 下载 → 重启安装
- [ ] 升完版本号显示 0.1.1，聊天/文件功能正常

### 4.4 兜底：静态更新源 / 纯手工分发

**A. 静态更新源（不走管理台，脚本链路）**——注意清单里的 URL 必须写成服务器地址：

```bash
cd /Users/pengzuyu/Documents/trae_projects/baobao-work
BBC_PUBLIC_URL=http://<SERVER_IP> node scripts/release/gen-manifest.mjs --version 0.1.1
# 产出 out/release/v0.1.1/{latest.json,release-info.json}（URL 指向 http://<SERVER_IP>/update/releases/...）
scp -r out/release/v0.1.1/{latest.json,release-info.json} <user>@<SERVER_IP>:/tmp/upd/
scp -r out/release/v0.1.1/windows-x86_64 <user>@<SERVER_IP>:/tmp/upd/releases/v0.1.1/
# 服务器上：
cd baobaochat-deploy-v0.1.5/compose
cp /tmp/upd/latest.json /tmp/upd/release-info.json volumes/updates/
mkdir -p volumes/updates/releases/v0.1.1 && cp -r /tmp/upd/v0.1.1/windows-x86_64 volumes/updates/releases/v0.1.1/
```

> ⚠ 别直接拷 `out/release/v0.1.1/latest.json`（那是本机用 `http://localhost` 构建的测试清单，
> 客户端会去连 localhost）。必须用 `BBC_PUBLIC_URL=http://<SERVER_IP>` 重新生成。
> 动态清单（管理台）有数据时优先；静态文件只在动态 404 时兜底，两套可共存。

**B. 纯手工分发**：直接把 `BaobaoChat_0.1.1_x64-setup.exe` 放内网文件共享给用户安装。
功能完全正常，只是**没有「检查更新」自动升级**、官网下载区不展示。

## 5. 日常运维

```bash
cd compose

# 日志
docker compose logs -f app            # 业务日志
docker compose logs --tail=100 nginx-lb

# 备份（pg_dump + 配置 + 证书 → volumes/backup/）
./backup.sh
./restore.sh <备份文件>               # 恢复

# 升级：先 load 新镜像，再一键（磁盘预检→备份→迁移→滚动→健康检查）
docker load -i ../images/bbc-app-<新ver>.tar.gz
./upgrade.sh <新ver>
./rollback.sh <上一ver>               # 升级失败时

# 对象存储控制台（仅本机/SSH 隧道）
ssh -L 9001:127.0.0.1:9001 <user>@<SERVER_IP>   # 浏览器开 http://127.0.0.1:9001
```

**端口/防火墙**：只需放行 **80/tcp**（443 备用）。pg(5432)/redis(6379)/rustfs(9001) 均绑定 127.0.0.1。
**磁盘**：数据卷 `pg-data`、`rustfs-data`；水位 >80% 要告警，>85% 升级会主动阻断。
**数据卷位置**：`docker volume ls | grep baobao-chat`；如需快照，对 `pg-data`/`rustfs-data` 做宿主机级快照。

## 6. 可选：启用 OIDC（生态应用用 BaobaoChat 账号登录）

纯内部聊天/Agent/文件不需要；要让其它系统接 BaobaoChat 登录时再开（不停服、不重建数据）。

```bash
cd baobaochat-deploy-v0.1.5
bash gen-oidc-key.sh >> compose/.env      # 生成并追加两行
vi compose/.env                           # 把 BBC_OIDC_ISSUER=CHANGE_ME 改成 http://<SERVER_IP>
cd compose && docker compose up -d app    # 只重启 app
```

```bash
curl -s http://<SERVER_IP>/oauth2/.well-known/openid-configuration | head -c 300
#   issuer 必须与 .env 的 BBC_OIDC_ISSUER 完全一致
```

生态应用接入：授权 `/oauth2/authorize`、token `/oauth2/token`、公钥 `/oauth2/keys`；
管理后台 → **登录接入** 里登记 client（public client + PKCE）。

## 7. 排障速查

| 现象 | 先查什么 | 处理 |
|---|---|---|
| nginx-lb 反复重启，日志 `cannot load certificate` | `ls compose/volumes/certs/` | 缺证书；按 2.3 的「证书」段补 `tls.crt/tls.key` 后重启 |
| 网页打不开/502 | `docker compose ps`、`logs app` | app 未起：多为 DB 连不上（`.env` 里 `BBC_DB_DSN` 与 `POSTGRES_PASSWORD` 不一致） |
| `/setup` 一打开就 404 或直接登录页 | `curl /api/v1/setup/status` | 已有用户即关闭向导是正常；忘记口令走管理后台重置 |
| 上传头像/文件失败 | `docker compose logs app \| grep -i presign` | 99% 是 `BBC_S3_PUBLIC_ENDPOINT` 没改成 `http://<SERVER_IP>/oss` |
| 客户端发布上传报错 | 同上一行 | 同上（D39 直传也走预签名） |
| Agent 不回话 | 管理后台 AI 供应商页 | Key 未填/无效；确认 `BBC_KMS_MASTER_KEY` 未被改 |
| 客户端登录报网络错误 | `netstat -ano \| findstr :80`（Windows） | 客户端出包地址 ≠ 部署地址 → 重出客户端包 |
| `/update/latest.json` 404 | 管理台客户端发布页 | 未发布任何版本属正常（回落静态也没有）；上传并「发布」后变 200 |
| 官网下载区空 | `curl /update/release-info.json` | 同上；或官网静态未随包（compose/volumes/website 为空时显示占位提示） |

**常用定位命令**

```bash
docker compose ps
docker compose logs --tail=200 app
docker compose exec pg psql -U bbc -d bbc -c "select count(*) from schema_migrations;"
curl -sv http://<SERVER_IP>/healthz
```
