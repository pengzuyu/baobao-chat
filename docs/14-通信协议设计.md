## 2. WSS 连接与信封

### 2.1 连接建立与保活

```
wss://host/ws/connect?token=<access JWT>&did=<deviceId>&v=1
```

- 认证失败返回 4001 后关闭；成功后服务端注册在线（Redis `t:{tid}:online:{uid}`）。
- 心跳：客户端每 30 s `ping`（信封 type=ping），服务端回 `pong`；60 s 无心跳判定半开，断开。
- 重连：指数退避 1s,2s,4s,…上限 60s + 抖动；重连成功立即执行 §4 同步。

### 2.2 消息信封（JSON，UTF-8）

```json
// 请求（客户端→服务端，需服务端 ack）
{ "v": 1, "id": "c-12345", "type": "msg.send", "ts": 1760000000000, "payload": { ... } }
// 服务端 ack（对请求的成对回执）
{ "v": 1, "id": "s-88801", "ack": "c-12345", "type": "msg.send.ack", "code": 0, "payload": { ... } }
// 服务端推送（无对应请求）
{ "v": 1, "id": "s-88802", "type": "msg.new", "ts": 1760000000123, "payload": { ... } }
```

| 字段 | 说明 |
|---|---|
| v | 协议大版本，当前 1 |
| id | 消息 ID，`c-`（client）/`s-`（server）+ 雪花/自增 |
| ack | 成对回执指向的请求 id |
| code | ack 中 0=成功，非 0=错误码（§7） |
| type | 事件类型，命名 `域.动作`（点分层级） |

规则：

- 客户端请求 10 s 未收到 ack → 超时重试（幂等，见 §5.3）；3 次失败进入 failed 态由 UI 处理。
- 服务端到客户端的推送不需要客户端逐条 ack（可靠性由同步机制保证，§4）。
- 二进制仅在媒体面（WebRTC）与文件分片（预签名 PUT body）出现，信封内不携带二进制。

### 3.3 Agent 相关流量说明（重要）

- Agent 的 **LLM 流量不走 WSS**：Runtime 以 OBO token 直连 ai-gateway（HTTPS+SSE），避免大流量长文本冲击信令通道。
- Agent 的 **工具调用直接访问各服务 REST**（OBO token），同样不走 WSS。
- UI 对 Agent 的状态展示（流式输出、权限确认卡）走**本地 stdio JSONL → Tauri 事件**（08 篇），不经服务端。
- **例外——任务终态跨端通知（OQ-C32 定稿）**：run 进入终态（done/failed/cancelled）时，宿主以用户 OBO token 调 `POST /api/v1/notify/agent-tasks` 上报（幂等键 `run_id`；D16 run 快照字段）；notify 域落事件后三路分发：① 推该用户**其它在线设备** `agent.task.completed`（跨端提醒，本地设备已由 Tauri 本地通知触达）② 通知中心落卡（`notification.new`，kind=agent，D03 PIM-09）③ 匹配 bot Outgoing 订阅（20 篇 §4.3 事件源③，S5 场景）投递外部系统。上报失败不阻塞本地（本地重试 3 次后放弃，跨端通知为尽力而为）。
- 服务端仅在以下情况推送：`agent.revoked`、`ai.quota.warning`、`agent.task.completed`。

## 4. 消息可靠性：seq 游标与增量同步

### 4.1 序号体系

| 序号 | 生成 | 用途 |
|---|---|---|
| client_msg_id | 客户端 UUID | 发送幂等（重试不重复落库） |
| seq | 服务端、**会话内**单调 +1 | 会话内全序、多端同步游标 |
| timeline_id | 服务端、**用户级**单调 | 联系人消息流/通知排序等弱序场景 |

### 4.2 登录/重连同步流程

```
客户端 → REST GET /api/v1/sync?cursors={convA:120, convB:88,...}&limit=200
响应: { convs: [ {conv, messages:[seq>cursor…], latest_seq, unread},
                 {conv, gap:true, total_behind:5000, fetch_url} ],
        presences, badges, server_ts }
客户端处理: 顺序落 SQLite → 更新游标 → UI 增量渲染
超大缺口(如3周未登录): 只拉最近 limit 条 + 提示"加载更早"翻页拉取(游标分页)
```

- 多端一致：每端独立游标；服务端漫游保留默认 180 天（租户可配 30–3650）。
- 补洞：会话内检测 seq 不连续 → `GET /messages?after=120&before=131` 精确补拉。

### 4.3 顺序与时间

- 会话内显示顺序以 `seq` 为准（服务端分配，天然有序）。
- 会话列表排序以最新消息服务端 `ts` 为准。
- 跨端时钟偏差不影响正确性（不信任客户端 ts，仅作展示参考）。

## 5. REST 规范

### 5.1 通用约定

| 项 | 约定 |
|---|---|
| 路径 | `/api/v1/<域>/<资源>`，复数名词，动作走子资源（`POST /messages/{id}/recall`） |
| 认证 | `Authorization: Bearer <access JWT>`；Agent 调用同头 + token 含 `act` |
| 幂等 | 写操作带 `Idempotency-Key`（UUID）；服务端 24h 去重 |
| 分页 | cursor 式：`?cursor=&limit=`（默认 20，最大 100）；响应 `{items, next_cursor, has_more}` |
| 排序/过滤 | `?order=-ts&...` 显式字段白名单 |
| 限流 | 响应头 `X-RateLimit-Remaining`；429 + `Retry-After`；Agent 通道限流更严（03 篇§6.3） |
| 版本 | URL v1；不兼容变更升 v2 并保持 v1 兼容窗口 ≥ 6 个月 |
| 审计 | 所有写操作由网关/服务自动落 audit（03 篇） |

### 5.2 响应包

```json
// 成功
{ "code": 0, "data": { ... }, "trace_id": "..." }
// 失败
{ "code": 3004, "message": "消息内容超过长度限制", "details": {...}, "trace_id": "..." }
```

### 5.3 幂等重试矩阵

| 操作 | 幂等键 | 重试安全 |
|---|---|---|
| msg.send | client_msg_id | ✅ 重试返回原 seq |
| 文件 complete | upload_id | ✅ |
| 其余写操作 | Idempotency-Key 头 | ✅ |
| rtc.call.invite | call_id | ✅ |

## 8. 协议演进策略

- `v` 字段做大版本协商；服务端对旧版本维持兼容窗口（≥6 个月）。
- 事件 type 走注册表（本篇 §3），新增只增不改语义；字段废弃采用"双发一个窗口期"。
- 客户端遇到未知 type：忽略并上报埋点（前向兼容）。
- 各服务对 payload 定义 JSON Schema，代码生成 TypeScript 类型与 Go 结构体（前后端同源）。
