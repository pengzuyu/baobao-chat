## 1. 选型原则

用户对技术栈的三个硬约束，作为评估权重最高的维度：

1. **跨平台能力强（UI 层）**：Windows / macOS / Linux 三端一致，且 UI 能力足以承载 IM 聊天流、文档协同、Agent 工作台这类复杂界面。
2. **资源占用少**：作为全员常驻后台的办公软件，安装包、内存、启动速度是体验底线。
3. **页面易设计与调整**：界面迭代速度快、设计与还原成本低、人才市场好招。

附加约束（来自产品形态）：

4. 需要嵌入第三方 Web 文档编辑器（OnlyOffice/Collabora 本质是 Web 应用）→ **客户端必须内嵌 WebView**。
5. Agent 运行时需在用户本机以本人权限执行脚本、读写文件 → 需要一个**可分发、可独立进程管控的本地运行时**。
6. 私有化部署（内网/混合云），不依赖公网 SaaS。
7. 团队假设：有 Web 前端团队（必有）；Rust/Go 可接受少量投入（有备选）。

## 2. 桌面客户端框架（核心决策）

### 2.1 候选对比

| 维度 | Electron | **Tauri 2（推荐）** | Qt 6 / QML | Flutter Desktop | Avalonia (.NET) |
|---|---|---|---|---|---|
| 渲染内核 | 自带 Chromium | 系统 WebView（WKWebView/WebView2/WebKitGTK） | 自绘 | 自绘 Skia/Impeller | 自绘 |
| 安装包（本产品预估） | 90–160 MB | **8–20 MB** | 40–70 MB | 45–70 MB | 35–55 MB |
| 空闲内存（IM 常驻） | 350–600 MB | **150–280 MB** | 100–200 MB | 180–350 MB | 130–260 MB |
| 冷启动 | 1.5–3 s | **0.6–1.5 s** | < 1 s | 1–2.5 s | 1–2 s |
| UI 开发效率/人才池 | ★★★★★（Web） | ★★★★★（Web） | ★★（QML/C++ 稀缺） | ★★★（Dart） | ★★（C#/XAML） |
| 界面设计与热调整 | ★★★★★（热重载/设计生态） | ★★★★★（同 Web） | ★★★ | ★★★★ | ★★★ |
| 嵌 OnlyOffice 等 Web 编辑器 | 原生契合 | 良好（WebView + iframe） | 需内嵌浏览器组件，成本高 | 差（需 PlatformView 拼装，桌面不成熟） | 差 |
| 原生能力（托盘/通知/录屏/开机自启） | 成熟 | 成熟（官方/社区插件） | 最佳 | 插件质量参差 | 一般 |
| 多窗口/浮窗（通话 PiP） | 好 | 好 | 好 | 一般 | 一般 |
| 自动更新（内网自建源） | electron-updater 成熟 | tauri updater + 内网更新源，成熟 | 需自研 | 需自研 | 需自研 |
| 主要风险 | 资源占用口碑差、安全面大（Chromium 漏洞随包） | Linux WebKitGTK 兼容差异；部分原生插件质量 | 迭代慢、招聘难 | 桌面端文本编辑/输入法/多窗口细节坑多 | 生态小 |

### 2.2 结论：Tauri 2 + Web 前端

**推荐 Tauri 2**。理由：

- 三个硬约束全满足：Web 技术保证"页面易设计与调整"与跨平台 UI 一致性；系统 WebView + Rust 壳保证小体积、低内存；Rust 核心进程同时充当**本机能力层**（与 Agent Runtime 的进程管理、本地库、系统权限对接），一石二鸟。
- 嵌入 OnlyOffice（WebView 内 iframe）是本产品文档方案（见 §6）的必要条件。
- 自动更新、代码签名、sidecar（捆绑独立二进制）均为官方一等能力，Agent Runtime 以 sidecar 分发天然契合。

**风险与缓解**：

| 风险 | 缓解 |
|---|---|
| Linux WebKitGTK 与 Chrome 行为差异 | 内网可控终端，锁定支持矩阵（Win10+、macOS 12+、Ubuntu 20.04+/麒麟）；前端建立浏览器兼容 CI（Playwright 三端跑）；不支持的旧系统降级提供 Electron 备选包（方案 B，仅按需维护） |
| 系统 WebView 未安装（Win7 等旧机） | 安装器检测并引导安装 WebView2 运行时；或分发 Electron 备选包 |
| 某些原生插件质量参差 | 关键原生能力（托盘/通知/屏幕捕获/自动更新）只用官方或一线社区插件；缺失则 Rust 侧自研命令 |
| WebView 多进程内存受系统内核版本影响 | 内存预算与测试矩阵见 16 篇 §性能预算 |

**方案 B（备选）**：Electron + 同一套 React 前端。前端代码 100% 复用，仅 Tauri Rust 层需替换为 Node 主进程实现。保持"前端与原生层薄耦合"可在必要时切换。

## 3. 前端技术栈（UI 层）

| 层 | 选型 | 理由 | 备选 |
|---|---|---|---|
| 框架 | React 18 + TypeScript 5 | 生态最大、人才好招；TS 保证协议/数据模型类型安全（与后端共享 schema 类型） | Vue 3（若团队既有栈） |
| 构建 | Vite 5 | 秒级热更新，"易调整"的直接保障 | — |
| UI 组件库 | **Ant Design 5** | 企业级表格/表单/树/抽屉组件全（管理后台、权限编辑器刚需）；主题令牌体系便于统一设计 | Arco Design（更轻，IM 观感好，可作聊天区皮肤层） |
| 状态 | Zustand（客户端 UI 态）+ TanStack Query（服务端态缓存） | 轻量、样板少；消息/会话等列表态用本地持久化插件 | Redux Toolkit（重） |
| 消息流渲染 | 虚拟滚动（react-virtuoso）+ 稳定 key（`convId:seq`） | 万级消息流畅滚动 | — |
| Markdown/代码高亮 | react-markdown + Shiki | Agent 输出渲染刚需 | — |
| 富文本输入 | Slate 或 Lexical | 聊天输入框（@提及、表情、引用、截图粘贴） | — |
| 样式 | Tailwind CSS 3 + 设计令牌（AntD token 对齐） | 快速调整布局，统一间距/色板 | CSS Modules |
| 图表（管理后台） | ECharts 5 | 用量/审计可视化 | — |

> 原则：**聊天/Agent 工作台等体验层手写组件为主（AntD 为底），管理后台以 AntD 组件为主**，兼顾体验与效率。

## 4. Agent 运行时（自研，不用开源框架）

**结论：Rust 编写的独立本地进程（sidecar），随客户端分发，自研 Agent 循环，不引入 LangChain/LlamaIndex 等框架。**

| 决策点 | 结论 | 理由 |
|---|---|---|
| 语言 | Rust（tokio + reqwest + serde + git2 + notify） | 单二进制 10–15 MB；无 GC 抖动；权限校验/进程沙箱等安全代码放 Rust 侧最可靠；与 Tauri 核心同语言，复用工具链 |
| 与宿主通信 | stdio 上的 JSONL 消息（对齐 LSP 风格） | 进程隔离：Agent 崩溃不拖垮客户端；可独立升级；未来可暴露为 CLI（开发者可直接终端使用，像 zcode） |
| 为什么不用框架 | 自研循环 | Agent 核心循环（拼上下文→调模型→解析工具调用→执行→回填）本质 <2k 行核心代码；框架带来的抽象债（版本快、行为黑盒）在企业内网审计场景不可接受；工具协议自持（对齐 MCP 概念）便于生态接入 |
| LLM 接入 | OpenAI 兼容 API（内部 ai-gateway），SSE 流式 | 模型无关：网关后可挂 GLM/Qwen/DeepSeek 或 vLLM 私有化模型 |
| 模型路由 | 会话内可选"快模型/强模型"，复杂任务自动升档 | 成本与体验平衡 |
| 备选 | Go 实现 sidecar | 若团队无 Rust 储备；接口（JSONL 协议）不变即可替换 |

## 5. 服务端

### 5.1 语言与架构风格

| 决策点 | 结论 | 理由 |
|---|---|---|
| 语言 | Go 1.22+ | 单静态二进制便于私有化交付；goroutine 承载长连接（10 万级 WS 连接/节点）；内存占用低 |
| 架构风格 | **模块化单体起步**（单二进制多模块：auth/org/message/file/kb/app-registry/admin/audit），媒体节点与文档服务独立部署 | 私有化交付友好（小租户一套 compose 起全量）；模块边界按服务接口（Go interface）约束，规模大后可拆微服务（02 篇 §服务清单） |
| HTTP/WS | 标准库 + gin；WS 用 nhooyr/websocket | 轻量成熟 |
| 内部通信 | 进程内接口调用；拆分后 gRPC | 避免早期分布式复杂度 |
| 若公司为 Java 栈 | 可平移 Spring Boot 3 + Netty | 协议（14 篇）与架构不变，仅实现语言替换；在本设计中作为等价备选标注 |

### 5.2 存储与中间件

| 组件 | 选型 | 用途 | 备选 |
|---|---|---|---|
| 主库 | PostgreSQL 16 | 业务库 + JSONB（消息扩展）+ 分区表（消息按月）+ **pgvector**（知识库向量）+ zhparser（中文全文检索） | 消息量大后检索迁 OpenSearch |
| 缓存/队列 | Redis 7 | 在线状态、seq 游标缓存、presence 广播、限流、轻量任务队列（Stream） | NATS（若需更重队列） |
| 对象存储 | MinIO（S3 API） | 文件/图片/文档本体、缩略图、应用与技能包分发 | 兼容任何 S3（企业已有存储可直接换） |
| 全文检索 | PG FTS（zhparser）起步 | 消息/文档/知识库关键词检索 | >500 万活跃文档再引 OpenSearch |
| 向量 | pgvector（HNSW） | 知识库嵌入检索，运维面最小 | Milvus（>千万级向量再评估） |
| 嵌入/重排模型 | bge-m3（嵌入）+ bge-reranker-base（重排），经 ai-gateway 统一暴露 | 中文效果好、可私有化 | 供应商 API |

### 5.3 音视频

| 决策点 | 结论 | 理由 |
|---|---|---|
| 媒体传输 | WebRTC（客户端浏览器原生栈，Tauri WebView 直接支持 getUserMedia/RTCPeerConnection） | 免自研编解码；端到端 SRTP 加密 |
| SFU | **mediasoup v3**（独立 Node 媒体节点，media-svc） | C++ 编解码核心 + Node 控制面；成熟稳定、层级/路由 API 清晰；1v1 走 P2P 不经服务器（内网同段直连），多人走 SFU |
| 信令 | 复用客户端已有 WSS 连接（rtc.* 事件，见 14 篇） | 不新开信令通道，鉴权统一 |
| 穿透 | coturn（内网基本用不上，跨园区/VPN 场景兜底） | 标准组件 |
| 备选 | LiveKit（自托管 SFU，功能全但整体引入较重）；Pion 自研 SFU（完全可控但成本高） | mediasoup 折中：核心库级引入而非平台级 |

### 5.4 在线文档（Word/Excel/PPT）

| 方案 | 编辑保真度 | 部署 | 许可 | 结论 |
|---|---|---|---|---|
| **OnlyOffice Document Server（CE 自托管，WOPI 协议）** | OOXML 保真度业界开源最佳 | Docker 独立服务，接 MinIO | AGPL v3（自托管内部使用可接受；介意则购商业授权） | ✅ 采用 |
| Collabora Online（LibreOffice 内核） | 复杂排版/宏兼容一般 | 同上 | MPL | 备选（许可更宽松场景） |
| WPS 云文档/办公私有化 | 最佳 | 商业采购 | 按年付费 | 若公司已采购 WPS 私有化，则切换对接（接口层隔离） |
| 纯预览（LibreOffice headless 转 PDF）+ 禁编辑 | — | 轻 | MPL | 作为低端降级模式 |

集成方式：客户端 WebView 内 iframe 加载 OnlyOffice 编辑器；文件与权限经自研 doc-svc 以 **WOPI 协议**对接（访问凭证短时效、按用户鉴权）。详见 06 篇。

### 5.5 AI 模型接入

| 决策点 | 结论 |
|---|---|
| 网关 | 自研 ai-gateway（Go）：OpenAI 兼容入口，后端可路由 GLM / Qwen / DeepSeek / vLLM 私有模型 |
| 凭证 | 模型 API Key 只存服务端（KMS/加密配置）；客户端与 Agent Runtime **不持有**模型密钥，用用户 token 走网关 |
| 计量 | 按租户/用户/会话计量 token 用量，供配额与成本分摊（12 篇用量模块） |
| 安全 | 网关侧内容脱敏开关、敏感词、审计采样（可配） |

## 6. 最终技术栈总表

| 层 | 技术 |
|---|---|
| 客户端壳 | Tauri 2（Rust 核心 + 系统 WebView），多窗口、系统托盘、全局快捷键、自动更新 |
| 前端 | React 18 + TypeScript + Vite + Ant Design 5 + Tailwind + Zustand + TanStack Query |
| Agent Runtime | Rust sidecar（自研循环，stdio JSONL 协议，OpenAI 兼容流式） |
| 客户端本地库 | SQLite（消息缓存/会话/Agent 会话）、系统钥匙串（凭据） |
| 服务端 | Go 模块化单体（auth/org/message/file/doc/kb/app-registry/admin/audit/notify）+ gateway 独立部署 |
| 媒体 | mediasoup SFU（media-svc）+ coturn + WebRTC |
| 文档 | OnlyOffice Document Server CE（WOPI）+ LibreOffice headless（预览降级） |
| 数据 | PostgreSQL 16（pgvector + zhparser + 分区）、Redis 7、MinIO |
| AI | ai-gateway（OpenAI 兼容）→ GLM/Qwen/DeepSeek/vLLM；bge-m3 + bge-reranker |
| 交付 | 客户端：Tauri updater（内网更新源 + 签名 + 灰度通道）；服务端：docker-compose（小规模）/ K8s（中大规模） |

## 7. 明确不引入 / 延后

| 项 | 处理 | 原因 |
|---|---|---|
| LangChain / LlamaIndex 等 Agent 框架 | 不引入 | 自研循环（§4）；避免黑盒与版本风险 |
| Electron 作为主方案 | 降为方案 B | 资源占用 |
| OpenSearch | 延后 | PG FTS + zhparser 起步够用 |
| Milvus | 延后 | pgvector 覆盖预期规模 |
| 移动端（Tauri 2 iOS/Android） | 预留 | 协议层预留 `v` 与轻量端能力，产品二期评估 |
| E2EE 消息加密 | 延后 | 与审计/合规检索冲突，作为高保密租户的可选特性设计（15 篇） |

## 8. 开放问题

1. 公司是否有既有 Java 中间件规范（注册中心/网关）需要贴合？影响服务端形态从"模块化单体"调整的时点。
2. 是否已有 WPS/腾讯文档私有化采购？若有，文档层切换为对接该服务（接口已隔离，影响可控）。
3. GPU 资源：知识库嵌入与重排是否独立 GPU 节点部署？影响 16 篇容量规划。

### A.3 结论

私有化内部部署形态下，全栈无强制开源义务与采购项（可选商业项：OnlyOffice 商业授权、WPS）。对外多租户 SaaS 化前，按 A.2 逐项复核即可。
