## 3. 部署拓扑与容量规划

### 3.1 小规模：单 VM docker-compose（≤2k 用户）

```
                        企业内网 · 单VM（docker-compose）
┌────────────────────────────────────────────────────────────────────────┐
│ 客户端 / 浏览器(Web管理台)                                               │
│   │ https/wss 443                          ┌──────────────────────┐    │
│   ▼                                        │ update-src           │    │
│ ┌──────────────┐    ┌───────────────────── │ 静态文件+版本清单     │    │
│ │ nginx-lb     │───▶│ app ×2（模块化单体：  │ (manifest, §5.1)     │    │
│ │ TLS 终止     │    │ auth/org/message/    └──────────────────────┘    │
│ │ WS 长连接    │    │ file/doc/kb/admin/                               │
│ └──────┬───────┘    │ audit/notify/app-registry/ai-gateway)           │
│        │            └──┬──────────┬──────────┬────────────────┬──────┘    │
│        ├──▶ onlyoffice ◀─(WOPI)   │          │                │           │
│        ├──▶ media（mediasoup，UDP 40000–50100 段）│              │           │

│        ▼             ▼                    ▼                        ▼           │
│ ┌──────────┐  ┌──────────┐  ┌───────────────────────┐  ┌──────────────┐    │
│ │ pg 16    │  │ redis 7  │  │ minio（单节点 2TB）    │  │ backup       │    │
```

要点：app ×2 提供滚动升级与单实例故障冗余；nginx-lb 做 TLS 终止与 WS 会话保持（ip_hash 或按 did）；media 与 app 同 VM 时独占 UDP 端口段。

### 3.2 中大规模：K8s（≤20k 用户/租户，多租户托管）

| 组件 | 形态 | HPA 指标 | 亲和性/特殊约束 |
|---|---|---|---|
| gateway | Deployment ×N | **在线连接数**（目标 3.5 万/实例，上限 5 万，§6.7） | 多可用区打散；PDB minAvailable=1 |
| app（域模块拆分：auth/org/message/file/doc/kb/admin/audit/notify/app-registry/ai-gateway） | 各自 Deployment | CPU 70% + 各域队列深度（file/kb worker） | message/admin 就近 PG；audit 独立节点组（追加写负载） |
| media | Deployment ×N | 房间数/转发流数 | **hostNetwork + UDP 40000–50100 端口段独占**；节点污点隔离；每节点固定可配端口范围（§3.3） |
| onlyoffice | Deployment ×N | 并发编辑会话数 | 与 doc 同机房；会话粘滞 |
| coturn | Deployment ×2 | — | DaemonSet/NodePort，跨园区场景才启用 |
| PostgreSQL | **Operator（CloudNativePG 类）或 StatefulSet + StorageClass** | — | 主从流复制 + 1–2 读副本；WAL 归档至对象存储（§4.6） |
| Redis | StatefulSet 哨兵 3 节点 | — | 仅缓存/队列，持久化按需（AOF 关闭优先） |
| MinIO | 分布式 StatefulSet（4+ 节点） | — | 纠删码 EC:2；跨站点复制可选（§4.6） |
| update-src | Deployment ×2 + 内网 CDN/静态分发 | 带宽 | 版本清单与安装包缓存双活（§7.3 演练项） |
| 可观测栈 | prometheus/otel-collector/grafana/alertmanager | — | 独立 namespace；指标保留 30d |

### 3.4 双形态部署等价性（Docker 与 K8s 均为一等公民）

> 原则：**同一组镜像、同一套配置键、两份编排**。两种形态功能完全等价（含 Agent/知识库/文档/通话全部能力），差异只在伸缩、自愈与多租户密度；禁止出现"仅 K8s 支持"的功能项（托管增强除外）。

**统一镜像清单**（两形态共用，版本由同一 tag 锁定）：

| 镜像 | 基础镜像 | 端口 | 健康检查 |
|---|---|---|---|
| bbw-app | distroless | 8080 | /healthz · /readyz（模块由 `--enable` 控制） |
| bbw-gateway | distroless | 8081 (http+ws) | /healthz |
| bbw-media | ubuntu（内核依赖） | 8082 tcp + 40000–50100/udp | /healthz |
| bbw-update-src | nginx-alpine | 80 | 静态探测 |
| 第三方（版本钉死） | postgres:16 · redis:7 · minio · onlyoffice/ds · coturn · clamav(可选) · prometheus/grafana/otel-collector(运维栈) · **邮件栈（可选 profile "mail"，22 篇）：docker-mailserver 或 postfix/dovecot/rspamd 组件组 或 stalwart** | — | 各自官方 |

**配置等价映射**（配置键名完全一致，仅来源不同）：

| 统一配置键 | docker-compose 来源 | K8s 来源 |
|---|---|---|
| BBW_DB_DSN / BBW_REDIS_ADDR / BBW_S3_* | `.env` | Secret `bbw-db` / `bbw-s3` |
| BBW_TLS_*（含企业 CA） | `volumes/certs/` | TLS Secret |
| BBW_FEATURE_*（特性开关） | `.env` | ConfigMap + feature_flag（§5.3） |
| 模块启停 | compose **profiles**（core/media/docs/ops） | Helm `values.modules.*` |

**交付物结构**：

```
deploy/
├─ compose/                          # Docker 形态（单 VM 或双 VM）
│  ├─ docker-compose.yml             # 全量拓扑（profiles 分组启停）
│  ├─ .env.tpl                       # 全部配置键+注释（与 Helm values 一一对应）
│  ├─ init/                          # 首次部署：CA 引导、平台管理员、migrate job、邮件域 DNS 五项检测（22 篇：MX/SPF/DKIM/DMARC/autodiscover）
│  ├─ upgrade.sh / rollback.sh       # 备份→拉镜像→按 §4.4 顺序逐服务 recreate→健康检查
│  ├─ backup.sh / restore.sh         # §4.6 单机实现
│  └─ README                         # 硬件门槛/端口清单/防火墙矩阵
└─ helm/bbw/                         # K8s 形态
   ├─ values.yaml（默认小规模）· values-mid.yaml · values-large.yaml
   └─ templates/（一组件一文件：app/gateway/media/pg/redis/minio/onlyoffice/
      hpa/pdb/ingress-tls/configmap/secret[可接 external-secrets]）
```

**双形态升级/回滚路径**：

| 环节 | docker-compose | K8s |
|---|---|---|
| DB 迁移 | upgrade.sh 内置 migrate job（同镜像 `bbw-app migrate`） | helm pre-install/upgrade Job |
| 滚动 | 按 §4.4 顺序逐服务 recreate + /healthz 探测 | Deployment 滚动 + readinessGate |
| 回滚 | 保留上一 tag 一键切回（DB 依赖迁移向后兼容承诺，§4.4） | `helm rollback` |
| media 特殊性 | 独立 profile + 通话避让窗口提示 | PDB + 通话避让（drain 前检查在线房间） |

**形态选择判据**：≤2k 用户/单 VM/无自愈要求 → compose；多租户托管/HPA 自愈/灰度发布 → K8s。两者可相互平移（数据卷与对象存储兼容导出）。

### 4.1 客户端构建、签名与公证

```
CI 流水线（三平台矩阵构建）
 1 拉起构建容器（锁定工具链版本）→ cargo/tauri build + 前端 Vite 构建
 2 前端产物注入构建号/更新通道元数据
 3 签名：
   ├ Windows：Authenticode（私钥在签名机/HSM）；时间戳用内网 RFC3161 服务，
   │           离线时预取并缓存时间戳令牌
   ├ macOS：Developer ID 签名 → notarization 公证 → stapler 装订
   └ 更新包：ed25519(minisign) 签名 + sha256（与 10 篇应用包签名链同体系，15篇§3.3）
 4 产出入库（制品库）→ 发布到更新源（§5.1 manifest 更新，双签过渡按 15 篇§4.1）
```

**内网离线公证预案**（macOS notarization 依赖 Apple 服务）：

| 方案 | 说明 |
|---|---|
| 专线/代理白名单 | 构建机仅放行 apple 公证服务域名（notarytool），最小化外联 |
| 批量预公证缓存 | 发布窗口前集中公证并缓存装订结果，网络中断期分缓存产物 |
| 极端离线 | 经 MDM 分发带组织自签的企业 pkg + 终端 Gatekeeper 白名单策略；仅限受控终端，文档声明该模式风险 |

### 4.2 客户端更新机制

| 机制 | 设计 |
|---|---|
| 更新源内网化 | 静态文件（安装包 + 版本清单 manifest，§5.1）置于 update-src / MinIO 前置 CDN；无任何公网回源 |
| 检查节奏 | 启动时 + 每 6 h 拉取 manifest；WS 不推送客户端自身更新（应用/技能包更新除外，走 `app.updated`） |
| 灰度通道 | **stable / beta 两通道** + **按百分比**放量（manifest.rollout.percentage）+ 部门/白名单定向；beta 通道供 IT 与自愿尝鲜者 |
| 强更 | manifest.force 含 `min_version` 与 `deadline`：低于 min_version 阻断登录并引导下载（登录页也内置检查端点 `GET /api/v1/client/bootstrap`）；deadline 到期后全量强制 |
| 跳版本 | 允许跨多版本直更：分发**全量包**（不做链式增量）；本地 SQLite schema 按"缓存可丢弃"设计（大版本允许清缓存重建，04 篇同步机制兜底） |
| 回滚 | **受控回滚**：发布"回滚版"（版本号继续递增，内容回退），复用灰度通道；不直接降版本号，避免触发 15 篇§3.4 降级防护 |
| 失败自愈 | 更新安装失败自动回退当前版本并上报指标；连续失败率 >1% 自动暂停放量（发布看板联动 12 篇§4.4 看板模式） |

### 4.3 Agent Runtime sidecar 捆绑与独立热更

1. **捆绑**：安装包内置 Agent Runtime 基线版本与"主程序最低兼容版本"元数据（§5.1 manifest.agent_runtime）。
2. **独立热更**：Runtime 自身版本经更新源分发（与应用/技能包同通道风格，10 篇），客户端校验签名后**原子替换二进制并重启 sidecar 进程**，主程序不重启。
3. 兼容矩阵：manifest 声明 `min_compatible`；主程序升级时若捆绑版本较新清单落后 → 后台静默更新 Runtime；不满足兼容窗口则阻止主程序降级安装。

### 4.4 服务端版本升级顺序（先服务端后客户端）

```
0 预检：兼容矩阵核对 / 磁盘水位 / 备份健康检查（§4.6）
1 备份：PG 基础备份 + WAL 确认可归档
2 DB 迁移：仅向后兼容变更（加列/加表/新索引 CONCURRENTLY）；窗口内禁破坏性变更
3 服务端滚动升级：audit/notify → 域服务（org/message/file/doc/kb/...）→ auth
   → gateway 最后（接入层最后切换，保证旧客户端协议兼容）
4 验证：冒烟用例 + SLO 观察 24 h（§6.6 错误预算未耗尽方可继续）
5 客户端灰度：beta → stable 百分比爬坡；协议 v 兼容窗口 ≥6 个月（14篇§8），
   即：客户端可在服务端升级后 6 个月内继续使用旧协议版本
回滚：保留 N-1 镜像与迁移逆脚本（仅迁移窗口内有效）；超出窗口的回滚 =
      恢复备份（RTO 走 §4.6），故破坏性变更必须拆分为多窗口渐进执行
```

### 4.5 扩容与缩容

| 对象 | 扩容流程 | 缩容流程 |
|---|---|---|
| gateway/app | HPA 自动（连接数/CPU）或加副本滚动生效 | 手动降副本（先摘流量再缩，WS 优雅迁移：通知重连） |
| PG | 加读副本（流复制）→ 修改读路由 → 负载观察 | 摘除读副本路由 → 等连接归零再删 |
| media | 加节点 → 注册端口段 → 调度纳入 → 新房间调度到新节点 | 标记 draining → 现有通话结束不迁 → 下线 |
| MinIO | 加节点扩池（EC 重平衡，避开高峰） | 原则上不缩（先迁移数据再下线，容量评估前置） |
| 缩容红线 | — | 任何缩容前必须确认：备份成功 + 容量水位 <60% + 错误预算 >50% |

### 4.6 备份与恢复

| 对象 | 策略 | 目标 |
|---|---|---|
| PostgreSQL | **每日基础备份 + 连续 WAL 归档**（pgBackRest/WAL-G → MinIO 独立桶，独立凭据，不可删除 30 天） | **RPO ≤ 5 min / RTO ≤ 30 min（以演练实测为准）** |
| MinIO | 桶版本化（误删恢复）+ **跨站点复制（可选，高合规租户）**；备份桶独立凭据 | 版本回滚分钟级 |
| 配置与密钥 | compose/helm values + KMS 信封密钥的加密备份（15篇§3.3）；KEK 双人分持 | 恢复演练包含密钥恢复 |
| 客户端 | 无服务端备份（本地缓存可重建）；Agent 会话云端备份默认关（02篇§5） | — |

恢复流程：隔离环境拉起 → 基础备份恢复 + WAL 前滚至目标时点 → RLS/审计链校验（15篇§4.2）→ 应用冒烟 → 切流。

**季度灾难演练清单**：① PG PITR 恢复到隔离环境（实测 RTO/RPO 记录在案）；② MinIO 版本回滚与跨站点切换（若配）；③ 审计哈希链完整性校验；④ 证书轮换演练（预发环境）；⑤ media 节点故障转移（02篇§7）；⑥ 更新源故障 → 备用静态源切换；⑦ 全链路降级开关演练（IM-only 模式，§7.4）。

### 4.7 证书轮换（服务端）

```
预检（到期 <14d 告警）→ 内部 CA 签发新叶证书
 → 双证书部署（新旧并存，nginx/服务同时挂载）
 → 客户端固定的是根 CA（15篇§3.1 pinning），叶证书替换对客户端无感
 → 观察 24 h → 摘除旧证书 → 台账更新（15篇 security_key 思路同源）
根 CA 轮换：走"预置双根"策略（15篇§3.1），不在运维日常轮换范围
```

|---|---|

### 6.6 SLO 与错误预算
