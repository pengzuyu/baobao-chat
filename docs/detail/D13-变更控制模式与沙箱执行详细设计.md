# Part A · 变更控制模式

## A1. 正式命名与标识（全系统统一显示名）

| 官方中文名 | 协议标识（不变） | 一句话语义 | 面向用户 |
|---|---|---|---|
| **变更前确认模式** | `ask` | 任何变更（写文件/执行命令）前都先问你 | 新用户/敏感项目 |
| **自主模式** | `auto-edit` | 自主干活：文件修改自动执行；**危险命令仍需审批** | 日常开发主力档 |
| **完全控制模式** | `full-auto` | 全权委托：文件+白名单命令全自动，仅"永不全自动清单"保留审批 | 高信任/重复性任务 |

> 标识 `ask / auto-edit / full-auto` 在协议、审计、策略中原样保留（09/03/14 篇不改），中文名为 UI 官方显示名。旧文档中"权限模式"与"变更控制模式"同义，以本篇为准。

## A2. 能力矩阵（权威表，细化 09 篇 §3.1）

动作类别 × 模式的行为（✅自动执行 / 🔶需确认 / ⛔禁止）：

| 动作类别 | 变更前确认 | 自主模式 | 完全控制 | 备注 |
|---|---|---|---|---|
| 只读（read/list/search/glob/git status） | ✅ | ✅ | ✅ | 全档自动 |
| **文件编辑**（write/edit/git commit） | 🔶 逐次 | ✅ 自动（含检查点） | ✅ 自动 | 自主档起配 checkpoint |
| **白名单命令**（构建/测试/装依赖，项目 AGENTS.md 声明） | 🔶 | 🔶 首次确认，可记忆 | ✅ 自动（限时限资源） | 白名单来源见 A4 |
| **任意命令**（不在白名单） | 🔶 | 🔶 **每次确认（可编辑命令）** | 🔶 首次确认可记忆 | 自主模式的"危险命令需审批"即此行 |
| **高危命令**（规则库命中：rm -rf 系统路径/sudo/注册表/网络扫描…） | 🔶 双重提示 | 🔶 双重提示（**不可永久记忆**） | 🔶 双重提示（不可永久记忆） | 三档都不放行，见 A5 |
| 网络出站（http_fetch 白名单外/命令联网） | 🔶 | 🔶 | 🔶 | 永不全自动（数据外泄面） |
| **公司域写**（doc_write / im_send / app 写） | 🔶 | 🔶 | 🔶 | 永不全自动清单（09 篇 §6.4） |
| git push / 凭据使用 | 🔶 | 🔶 | 🔶 | 永不全自动 |
| ~~委派编码（coding.delegate）~~ | — | — | — | **已退役**（2026-11-19 委派域整域移除） |
| 子 Agent（只读探查） | ✅ | ✅ | ✅ | 修改类回主循环 |

> 核心规则：**子智能体的自主性不得高于当前档位**；**"永不全自动清单"与"高危命令"在任何档位都保留人工审批**——这是完全控制模式与"裸奔"的区别。

## A3. 配置层级与生效算法

```
生效档位 = min( 会话当前选择, 租户策略上限 agent_tool_policy.max_mode )
初始档位 = 用户默认设置；项目 AGENTS.md 可声明 mode.recommended 作为打开该项目时的建议初始值（提示一键切换）
```

| 层级 | 键 | 说明 |
|---|---|---|
| 租户策略（硬顶） | `agent_tool_policy.max_mode` | 管理台可设 ask/auto-edit/full-auto；禁用完全控制=租户内无人可进 full-auto（12 篇策略域） |
| 项目配置 | AGENTS.md `mode:` | 建议初始值（如生产仓库建议 ask） |
| 用户默认 | 设置→Agent | 个人常用档 |
| 会话当前 | 会话头部切换器 | 可随时向下切；**向上切需确认**（见 A4） |

进入完全控制模式的门槛（全部满足）：权限点 `agent:mode:full_auto` + 租户允许 + 该会话首次进入时二次确认（明确列出将放开的动作类别 + 沙箱状态必须≥标准档，见 B11）。

## A4. 升降级交互

| 交互 | 设计 |
|---|---|
| 切换器 | 会话头部胶囊（三档下拉）；当前档图标常显；`Cmd+Shift+M` 循环切换 |
| 升档确认 | 弹窗列出"将放开：文件编辑自动 / 白名单命令自动…"；显示当前沙箱状态徽标；确认后 `mode.changed` 入审计 |
| 降档 | 立即生效；**进行中已授权的命令不中断**（只拦后续），toast 告知 |
| 升档建议（不打断） | 同一会话连续批准 ≥5 次同类操作 → 审批卡底部出现"切换到自主模式可减少打断"链接，仅建议 |
| 高危命令双重提示 | 🔶 卡片红色描边 + 展开后果说明（规则库给出的理由），确认按钮需长按 800ms（防连点） |
| 审批超时 | 120s 无响应=拒绝（09 篇），会话若等待中可"稍后提醒"转通知中心 |

## A5. 危险命令规则库（三档通用的最后防线）

- 规则来源（优先级）：租户下发规则 > 内置正则库 > 模型分类兜底（09 篇 §4.4）；命中即"双重提示 + 禁止永久记忆"。
- 内置规则类别（示例）：破坏性删除（rm/rd 覆盖工作区外或系统路径）、提权（sudo/runas）、系统配置（注册表/systemd/launchctl）、凭据文件访问、网络扫描与抓包、包管理器全局安装、git push --force 到保护分支、fork 炸弹特征。
- 规则库热更：经租户策略通道（D02 §5 `policy.updated`）下发，bbrt-sec 规则引擎版本化。

## A6. 审计

`mode.changed`（from/to/触发者）入本地 JSONL 与会话镜像；完全控制会话在审计事件 `actor` 上附 `mode=full-auto` 标记（服务端 OBO 审计可见该会话档位）；升档确认的弹窗截图级记录不落盘（避免存敏感画面），仅记录确认时刻与文案版本号。

# Part B · 沙箱执行（无 Docker 的实现机制）

## B7. 先回答"zcode/trae 为什么不用 Docker"

| 维度 | Docker 方案 | **OS 原生原语（本设计）** | 纯工具门控（无 OS 沙箱） |
|---|---|---|---|
| 安装要求 | 需装 daemon/Docker Desktop；Linux 需 root 或 docker 组（≈root）；Win 的 Docker Desktop 有商业许可 | **零安装**（Linux bwrap 通常预装；macOS/Win 系统自带 API） | 无 |
| 启动延迟 | 秒级（卷挂载/镜像） | **毫秒级**（fork+exec 包装命令） | 无 |
| 文件可见性 | 需挂载映射，路径翻译破坏构建工具 | 直接见真实路径（只读绑定），构建/IDE 无感 | 全可见（靠白名单拦） |
| 隔离强度 | 最强（完整 ns+cgroups+overlay） | 强（mount-ns/Seatbelt/JobObject：防越界写、断网、限资源） | 弱（模型配合+路径检查，可被绕过） |
| 企业桌面可控性 | 差（IT 不给装） | 好 | 好 |

结论：Docker 本质是"namespaces + cgroups + 联合文件系统"的打包。**桌面 Agent 只取其中防误操作所需的原语**（mount 命名空间 / Seatbelt / Job Object），配合工具层门控——这正是 Claude Code（macOS 用 Seatbelt、Linux 用 bubblewrap 的 sandboxed bash）与同类工具的做法。

## B8. 威胁模型（诚实边界）

| 防 | 不防 |
|---|---|
| 模型被误导后的**越界写**（工作区外文件） | 内核漏洞/0day 提权 |
| **敏感读取**（~/.ssh、钥匙串、.env——工具层+只读绑定范围） | 用户自己在终端里主动运行的恶意程序 |
| **资源失控**（fork 炸弹、内存打爆、CPU 卡死） | 物理侧信道等高级攻击 |
| **意外数据外泄**（命令联网外传） | 已授权联网命令传"允许的内容"之外的数据（靠白名单+审计事后追责） |
| **进程残留**（僵尸/孤儿进程） | — |

## B9. 分层防御管线（run_command 实际执行路径）

```
L1 静态门控     模式矩阵(§A2) + 高危规则库(§A5) + 三级记忆 → 通过/需确认/拒绝
L2 工具层校验   路径白名单(工作区+临时目录) + realpath 符号链接逃逸检查(8024)
               + 敏感文件默认拒读(.env/*/id_rsa, 8026)
L3 OS 沙箱包装  按平台包一层(§B10)：限制可写范围 + 断网/网络策略
L4 资源限制     rlimit(CPU/AS/NOFILE/NPROC) + Linux cgroups v2(内存/进程数)
L5 生命周期     进程组(new session/pgid) + 超时(默认300s,8023) + 输出上限(1MB截断)
               + 取消: SIGINT→3s→SIGKILL 杀整树
L6 审计检测     JSONL 追加 + agent_sandbox_violation 记录 + 异常模式告警(高频写/批量删)
```

每层独立可验证；任一层失败 → 走 B11 降级（收紧而非放行）。

## B10. 各平台机制详表（bbrt-sec/sandbox/ 实现）

### Linux（隔离最完整）

| 能力 | 机制 | 说明 |
|---|---|---|
| 文件系统隔离 | **bubblewrap (bwrap)** mount 命名空间 | `bwrap --ro-bind / / --bind <workspace> <workspace> --bind <tmpdir> /tmp --proc /proc --dev /dev --unshare-net --die-with-parent --new-session -- <cmd>`：根只读、仅工作区与私有 /tmp 可写、**完全断网**；无需 root（user namespace） |
| 资源限制 | cgroups v2：`systemd-run --user --scope -p MemoryMax=2G -p CPUQuota=200% -p TasksMax=128` | 与 bwrap 组合；无 systemd 时退 rlimit |
| 断网 | `--unshare-net`（network namespace） | 需联网的构建：见下"联网例外" |
| 回退 | 无 bwrap → `unshare -m`（仅 mount ns）→ 无 → 纯 L1/L2+降级标记 | 探测顺序在沙箱健康检查中固化 |

联网例外（白名单命令需要网络时）：起**本地代理进程**（白名单域名/内网段才放行，其余拒绝并记 8025）——代理即 L3 的一部分，工作区外进程默认仍断网。

### macOS

| 能力 | 机制 | 说明 |
|---|---|---|
| 文件系统隔离 | **Seatbelt（sandbox-exec）编译型 profile** | profile 语义：`(version 1)(allow default)(deny file-write*) (allow file-write* (subpath (literal "/Users/x/ws")) ) (deny network*)`；即"全盘只读+仅工作区可写+断网" |
| ⚠ 状态 | Apple 标记 deprecated 但仍可用（Claude Code 同款方案） | 启动时 `sandbox-exec` 探测 + 最小命令冒烟；不可用 → 降级（B11）并跟踪未来替代（开放问题 1） |
| 资源限制 | `posix_spawnattr` + `setrlimit`（RLIMIT_CPU/AS/NOFILE/NPROC） | macOS 无 cgroups，尽力而为 + 监控杀超限（8022） |
| 进程树 | 同 POSIX 进程组（pgid）杀树 | |

### Windows

| 能力 | 机制 | 说明 |
|---|---|---|
| 资源限制 | **Job Object**：`JOB_OBJECT_LIMIT_JOB_MEMORY / PROCESS_MEMORY / KILL_ON_JOB_CLOSE / CPU_RATE_CONTROL`，子进程自动入 Job | 内存/进程数/CPU 硬限，超限整 Job 终止（8022） |
| 特权裁剪 | **Restricted Token**（CreateRestrictedToken 去掉管理员 SID 与特权）+ **Low Integrity Level** | 低完整性进程写中高完整性对象被拒 |
| 文件越界写 | 无 mount ns；靠 L2 工具层 + 低完整性 +（企业可选）**AppLocker/WDAC 规则**（MDM 下发，16 篇托管终端矩阵） | 诚实：Windows 是三平台最弱档，故完全控制模式在 Windows 上额外收紧（见 B11） |
| 网络 | 无原生断网 API → 白名单命令经本地代理；其余命令联网属 L1 确认范围 | 8025 审计兜底 |

### 跨平台汇总（能力 × 平台）

| 防护 | Linux | macOS | Windows |
|---|---|---|---|
| 越界写 | ✅ bwrap 只读根 | ✅ Seatbelt | 🔶 Low IL+工具层（+AppLocker 增强） |
| 敏感读 | 🔶 全盘可读（只读绑定）→ 靠 L2 拒读清单 | 🔶 同左 | 🔶 同左 |
| 断网 | ✅ unshare-net | ✅ deny network* | 🔶 代理白名单 |
| 内存/进程上限 | ✅ cgroups | 🔶 rlimit+监控 | ✅ Job Object |
| 超时杀树 | ✅ | ✅ | ✅（KILL_ON_JOB_CLOSE） |

> 敏感读在三平台都是"工具层拒读清单为主"——这正是为什么 `.env`/密钥文件规则（09 篇 §7.2）独立成层。

## B11. 沙箱降级矩阵（能力缺失时收紧而非放行）

| 探测结果 | 降级动作 | 用户可见 |
|---|---|---|
| bwrap 缺失（Linux） | 用 unshare -m；再缺 → 命令一律走"逐次确认"（等同 ask 档命令语义） | 会话头徽标"沙箱：基础门控" |
| sandbox-exec 不可用（macOS 新版若移除） | 同上：逐次确认 + 网络类命令一律拒绝 | 同上 |
| Windows（默认即弱档） | 完全控制模式**不可用**（自动上限=自主模式）；白名单命令也逐次确认 | 设置页说明 + 徽标 |
| 企业策略禁用 OS 沙箱（MDM） | 同缺失处理 | 租户策略下发 |

规则：**沙箱等级 < 标准档时，模式上限被压低**（完全控制不可进；自主模式的"自动文件编辑"保留——文件编辑有 checkpoint 可回滚，命令类全部收紧）。
