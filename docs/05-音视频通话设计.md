## 1. 功能概述

### 1.1 场景与规模

| # | 场景 | 说明 | 规模上限 |
|---|---|---|---|
| S1 | 1v1 音频/视频 | 私聊会话直接发起；**内网优先 P2P 直连**（同网段 ICE host 直连，媒体面不经服务器） | 2 方 |
| S2 | 群内多人通话 | 会话工具栏发起，成员点"加入"；走 SFU（mediasoup）转发 | 视频通话 **≤16 方**；纯音频 ≤64 方 |
| S3 | 屏幕共享 | 桌面/指定窗口共享；可与摄像头并存（视频 + 共享各一路 Producer） | 每参与者同时 1 路共享 |
| S4 | 通话卡片 | 通话结束/未接自动落会话消息流（`call_card`，04 篇 §1.2 已登记） | — |

技术基线（01 篇 §5.3）：WebRTC（Tauri WebView 原生 getUserMedia/RTCPeerConnection）；SFU 用 mediasoup v3 独立媒体节点（media-svc）；信令复用客户端已有 WSS（rtc.* 事件）；coturn 仅作跨园区/VPN 兜底。

### 1.2 设计原则

1. **信令与媒体分离**：WSS 只传控制面（邀请/SDP/ICE/状态），媒体面 SRTP/UDP 直连或经 SFU，互不阻塞。
2. **内网优先直连**：1v1 默认尝试 P2P，失败或劣化才升级 SFU（§7.2），节省服务器带宽。
3. **音频优先**：任何拥塞下降级顺序都是"先牺牲视频、保住音频"（§3.4）。
4. **秒级恢复**：媒体断流 1s 内检测、3s 内重连/迁移（02 篇 §7 对齐）。

### 1.3 非目标

PSTN 电话、通话录制与纪要（阶段四，预留 media-svc 插件位与 `rtc:record:start` 权限点）、跨企业互联、直播（>64 方走后续"频道"模型，04 篇开放问题）。

## 2. 角色与场景

| 角色 | 通话行为 |
|---|---|
| 普通成员 | 发起/接听 1v1 与群内通话、屏幕共享、邀请他人 |
| 部门/租户管理员 | + 通话策略配置（默认是否允许视频、最大时长）、通话记录合规查询（走 audit） |
| 审计合规员 | 通话元数据只读检索（参与者/时长，媒体内容不落库不审计） |

| 关键约束 | 说明 |
|---|---|
| 单设备单活动通话 | 同一设备同时只允许 1 个活动通话；新来电自动回 `rtc.call.busy` |
| 多端响铃 | 被叫所有在线端同时响铃，任一端接听/处理，其余端停止（rtc.state 广播） |
| 通话与消息共存 | 通话中消息照常收发；PiP 悬浮时点击消息可临时切回主窗 |

### 3.3 设备设置抽屉（通话中/预检均可打开）

| 分组 | 项 |
|---|---|
| 麦克风 | 设备选择、输入音量实时条、降噪开关（RNNoise 类，端侧） |
| 摄像头 | 设备选择、分辨率档（自适应/720p/1080p）、镜像预览 |
| 扬声器 | 设备选择、测试提示音、音量 |
| 虚拟背景 | **预留位**（阶段四：人像分割 + 图片/模糊，标注"未开放"） |

### 3.4 弱网指示器与降级联动

| 档位 | 判定（端侧 5s 滑动窗口） | 自动动作 |
|---|---|---|
| ● 良 | RTT<150ms 且 丢包<3% | 无 |
| ● 中 | RTT 150–400ms 或 丢包 3–10% | 视频自动降层（simulcast 低层）；提示"网络一般" |
| ● 差 | RTT>400ms 或 丢包>10% 持续 5s | 提示关闭视频（多人/SFU 下自动暂停发送视频）；音频保持 Opus + FEC/DTX |

重连横幅："正在重连…"（reconnecting 态，§4.4），≤10s 恢复或转 ended。

## 4. 核心交互流程

### 4.1 信令时序（复用 WSS，02 篇 §4.4 细化）

1v1：主叫 A、被叫 B（双端在线 B1/B2）：

```
A端            gateway/message-svc        media-svc         B1端        B2端
 │ rtc.call.invite │                        │                │           │
 │  {call_id,conv, │ ①建 call_session(ringing)               │           │
 │   media,offer}  │ ②目标端解析/在线检查                     │           │
 │◄──ack(call_id)──│ ③被叫任一端在通话中? ──是──► rtc.call.busy ──►A      │
 │                 │──────── rtc.ringing{call_id, 主叫信息, offer} ──────►│
 │                 │──────── rtc.ringing ───────────────────────────────► │
 │  振铃回执(486无) │                        │                │           │
 │ [A 听回铃音]     │                        │              用户点接听      │
 │                 │◄───────────────────── rtc.accept{call_id, answer, did} ┤(B2)
 │                 │── rtc.state{answered_elsewhere} ──► B1 停止响铃       │
 │  1v1: A↔B2 直接交换 SDP/ICE: rtc.signal {call_id, sdp|candidate} 双向经服务转发(不落库) │
 │                 │   P2P ICE 成功(host/srflx 直连) ──► 媒体面直连,不经 media-svc          │
 │                 │   P2P 失败(对称NAT/跨园区) ──► 向 media-svc 申请房间转 SFU / coturn relay│
 │◄═════════════════════ SRTP 媒体流（P2P 或经 SFU/TURN）═════════════════►│
 │ rtc.bye{reason} │ ④结束: 结算时长→call_card 落消息流(msg.new)→回收房间   │
```

群内多人：`rtc.call.invite{conv_id, media}` → 服务端向全部成员推 `rtc.ringing`（会话内同时落一条"通话进行中·加入"实时卡片，未加入者点击卡片或工具栏按钮即加入）→ 各参与者独立与 media-svc 经 `rtc.signal` 协商加入（新加入者不受发起时刻限制）。

通话中邀请他人：成员面板 "+" → 选择对象 → `rtc.call.invite`（复用同一 call_id，服务端只对新增被叫推 ringing）。

### 4.2 主叫视图状态机

```
                invite发出           收到对端振铃回执(rtc.ringing已触达)
  ┌──────┐ ────────────────► ┌─────────┐ ───────────────────► ┌─────────┐
  │ idle │                   │ dialing │                      │ ringing │
  └──────┘                   └────┬────┘                      └────┬────┘
      ▲                           │                              │ 对端 rtc.accept
      │                    rtc.call.cancel(主动取消)              ▼
      │                           │                          ┌───────────┐ ICE/DTLS
      │                    45s 无应答(no_answer)               │connecting │◄────┐
      │                    rtc.reject(rejected)                └────┬────┘     │ICE restart
      │                    rtc.call.busy(busy)                     │ ICE ok   │(网络切换)
      │                           │                              ▼          │
      │                           │                        ┌────────────┐   │
      │                           └───────────────────────►│ connected ├────┘
      │                                                    └──┬────┬────┘
      │                                          rtc.bye / 对端离开 │    │ 断流>1s
      │                                                        │    ▼
      │                                                        │ ┌─────────────┐ ≤10s恢复
      │                                                        │ │reconnecting │──────┘
      │                                                        │ └──────┬──────┘ 失败
      │                                                        │        │
      └────────────────────────────────────────────────────────┴────────┘
                                    ended{reason: normal|no_answer|canceled|
                                          rejected|busy|failed|network_lost|
                                          node_moved_final|timeout}
```

- 振铃超时 **45s**：dialing/ringing 合计 45s 无 accept → 服务端推 `rtc.state{no_answer}`，主叫端转 ended，落"未接来电"卡片。
- connecting 超时 10s（ICE 未成）→ ended(failed)。
- 通话最长时长默认 4h（租户可配），到点双方提示后结束。

### 4.3 被叫视图状态机

```
  ┌──────┐    rtc.ringing      ┌─────────┐  用户点接听 rtc.accept  ┌───────────┐
  │ idle │ ──────────────────► │ ringing │ ─────────────────────► │ accepting │
  └──────┘                     └────┬────┘                         └─────┬─────┘
     ▲   用户点拒接 rtc.reject      │  振铃45s未接(missed)              ICE/DTLS
     │   ────────────────────────► │ ─────────────────────► ended     │
     │   其他端接听(answered_        │                                    ▼
     │   elsewhere) rtc.state     ended                        ┌────────────┐
     │   ────────────────────────►                              │ connected ├─┐
     │                                                          └─────┬──────┘ │断流>1s
     │                              reconnecting(≤10s) ◄───────────────┘        │
     │   rtc.bye / 对端全部离开 ────────────────────────────────────────────────►│
     └──────────────────────────────────────────────────────────────── ended ◄──┘
                                  未接: missed → 红点 + 通知中心 + 未接卡片(回拨按钮)
```

被叫 missed（45s 未接）后：系统通知"未接来电（张三）"，会话内 call_card 带"回拨"按钮（一键 `rtc.call.invite` 反向呼叫）。

### 4.4 断流与重连

| 事件 | 检测 | 动作 |
|---|---|---|
| ICE 断流 | DTLS/RTP 超时 1s（getStats） | 进 reconnecting，横幅提示；尝试 ICE restart（网络切换 WiFi↔有线） |
| SFU Transport 断 | 同上 | 重新 `rtc.signal` 协商重建 Transport（凭证仍在有效期则免重邀） |
| media 节点故障 | 心跳丢失/网关判定 | 服务端推 `rtc.call.moved{new_node}`（本篇新增）→ 客户端 ≤3s 重连备用节点重建 Router/房间（§7.1）；1v1 直接回落 P2P |
| 重连超限 | reconnecting >10s | 转 ended(network_lost)；群通话卡片记录"网络中断退出" |

### 4.5 通话卡片（call_card）

| 状态 | 内容 | 交互 |
|---|---|---|
| 进行中（群） | "通话进行中 · 3 人 · 02:15"（实时） | 未加入者：[加入] 按钮 |
| 已结束 | 类型图标、时长、参与者头像列表、发起人 | 点击展开成员明细 |
| 未接（1v1） | "未接来电（张三）· 14:32" | [回拨] 按钮 + 红点 |
| 未接（群，受邀未加入） | "群通话已结束 · 未参加" | 点击查看参与明细 |

卡片由 message-svc 在通话结束时落流（系统侧生成，04 篇 `system`/`call_card` 渲染框架）；进行中卡片的实时状态经 `rtc.state` 更新，不重复落消息。

## 5. media-svc（mediasoup）房间模型

### 5.1 对象模型

```
call_session(逻辑房间, 记录在 message/media 共享元数据: Redis + PG)
   └─► Router(每通话每节点 1 个, 编解码路由器)
         └─► WebRtcTransport ×N(每参与者上行1 + 下行1)
               ├─ Producer(上行): audio(Opus, 不分层) / video(simulcast×3) / screen
               └─ Consumer(下行): 按订阅关系分发
订阅策略: 音频全订阅(静音轨道不消费); 视频按布局订阅——
   九宫格 ≤16 路取低/中层; 演讲者大画面取最高层; 后台参与者仅保留音频+小流
```

### 5.2 simulcast 三层

| 层 | 分辨率@帧率 | 用途 |
|---|---|---|
| 高 f | 1080p@30（共享内容 1440p） | 演讲者大画面 |
| 中 m | 720p@15 | 九宫格前排 |
| 低 l | 180p@8 | 九宫格缩略/胶片条 |

SFU 按 Consumer 下行带宽与布局动态选层（层切换 <500ms 无黑帧）；客户端上行始终三层同发（带宽不足时端侧先降高层的帧率/分辨率）。

### 5.3 编解码与音频优先

| 项 | 约定 |
|---|---|
| 音频 | Opus 48kHz，FEC + DTX + RED 冗余；优先级最高，拥塞时最后牺牲 |
| 视频 | VP8 默认（全平台兼容基线）；H.264 在三端硬编可用时协商启用 |
| 拥塞降级顺序 | 视频降空间/时间层 → 暂停非演讲者视频 → 暂停全部视频发送（提示"已为你关闭视频"）→ 音频降码率保连接 |
| 带宽估计 | transport-cc 端侧估计 + SFU maxOutgoingBitrate 调度（REMB 不使用） |

### 5.4 coturn 兜底

ICE candidate 收集：host（内网直连）→ srflx（STUN）→ relay（TURN/UDP 3478、TCP 443 备用）。内网同段 host 直连命中即完成；跨园区/VPN/对称 NAT 场景 P2P 失败 → TURN relay 或升级 SFU。TURN 使用短期凭证（HMAC 时限签名，GET /api/v1/rtc/config 获取，TTL 1h，随通话续取）。

## 6. 数据模型与接口

| 字段 | 类型 | 说明 |

| 权限点 | 默认角色 | 说明 |
|---|---|---|
| rtc:call:start | 普通成员 | 发起 1v1/群内通话 |
| rtc:meeting:schedule | 部门/租户管理员（03 篇已列） | 预约会议（阶段四启用） |
| rtc:record:start | 无（预留） | 通话录制（阶段四，需合规策略开启，15 篇联动） |

接听/加入不设权限点（会话成员即可），被移出会话者随 conv 成员失效自动无权加入。

## 7. 边界/异常/降级

### 7.1 媒体节点故障迁移

media-svc 节点健康状态上报 Redis（心跳 5s）；网关发现节点失联 → 判定受影响通话 → 服务端选备用节点重建房间 → 向所有参与者推 `rtc.call.moved{new_node}` → 客户端 **≤3s** 内向新节点重新 `rtc.signal` 协商重建 Transport（call_id 不变、成员关系在服务端元数据保留，无需重新邀请）。迁移失败 → ended(node_moved)；**1v1 通话在节点故障时优先回落 P2P**（02 篇 §7 策略），回落不成再迁移。

### 7.2 1v1 自动 P2P ↔ SFU 切换

| 阶段 | 规则 |
|---|---|
| 建立 | 先尝试 P2P（host/srflx 候选，内网成功率高）；3s 内 ICE 未成 → 升级 SFU |
| 通话中 | P2P 劣化（丢包>15% 或 RTT>500ms 持续 5s）→ 无缝升级 SFU：先建 SFU 流再断 P2P（双活 ≤2s，防冻屏） |
| 回落 | **单向升级防震荡**：本次通话升级 SFU 后不再回退 P2P；仅 media 故障时按 §7.1 回落 |
| TURN | P2P 阶段候选全败时先试 TURN relay，relay 质量仍差（RTT>300ms）→ 升级 SFU |

### 7.3 设备与权限异常

| 场景 | 处理 |
|---|---|
| 设备被其他应用占用 | getUserMedia NotReadableError → 提示"摄像头/麦克风被占用，请关闭占用程序"（5008）；可先以音频加入 |
| 本端已有活动通话 | 新来电自动 `rtc.call.busy`（单设备单通话）；多端场景由各端独立回 busy/接听 |
| 麦克风静音检测 | 发言提示"你处于静音状态"（说话能量检测 + 弹提示，防"忘开麦"） |
| macOS 屏幕共享权限 | 首次触发系统授权弹窗；未授权（5007）→ 分步引导：系统设置 → 隐私与安全性 → 屏幕录制 → 勾选 BaobaoWork → 重启应用（附示意图）；macOS 13+ ScreenCaptureKit 行为差异在客户端适配层抹平 |
| Linux 平台差异 | X11 直接捕获；Wayland 走 xdg-desktop-portal + PipeWire（Ubuntu 22.04+/麒麟 V10 SP1 支持，01 篇支持矩阵内）；V4L2 摄像头枚举差异由 Rust 侧设备抽象层归一；H.264 硬编不可用自动回 VP8 |
| 16/64 方边界 | 第 17 位开启视频的参与者：自动仅音频加入（提示"视频席位已满"）；纯音频上限 64（5002） |
| 多端加入 | 同一用户允许多端加入同一通话（call_member 按设备行）；第二端加入时提示"你已在其他设备加入"，可选择替换（旧端静音退出）或收听模式 |

### 7.4 其他边界

| 场景 | 处理 |
|---|---|
| 弱网（丢包 30%+） | 音频 FEC/RED 仍可维持；持续 30s 不可用 → 提示挂断重拨；自动降级链全走完才 ended |
| 群通话无人 | 全员离开后 30s 自动结束并落卡片 |
| 主叫取消 vs 被叫拒接 | 状态机区分 canceled/rejected，卡片文案不同（"已取消"/"对方已拒绝"） |
| 通话中成员被移出会话 | 权限失效：服务端向其推 rtc.state{removed} → 自动退出通话（03 篇权限收敛联动） |
| 时长计时 | 以服务端 connected_at/ended_at 为准（不信任端侧时钟） |
| 媒体安全 | DTLS-SRTP 全程加密；媒体内容不落服务端存储；仅元数据入审计（参与者/时长，15 篇定级） |

## 9. 开放问题

1. 视频席位从 16 扩展到更大（25/49 宫格）时 SFU 下行带宽模型与订阅策略需重新评估。
2. 网络切换（WiFi↔有线）ICE restart 的静音间隙是否可接受，是否需要双连接热备（成本高）。
3. mediasoup Router 是否按通话人数分级池化复用（小通话共享 Router）以降内存。
4. 通话记录是否支持"删除我的一段记录"（与审计保留策略的边界，需 12/15 篇定）。
5. Linux Wayland 下 PipeWire 共享的帧率上限（当前约 15–25fps）是否满足演示场景。
