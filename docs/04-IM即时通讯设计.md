## 1. 功能概述

### 1.1 定位

IM 是 BaobaoWork 的第一入口：私聊、群聊、广播群构成消息主干，文档卡片（06 篇）、文件消息（07 篇）、通话卡片（05 篇）、Agent 分享卡片（08/09 篇）都作为消息类型落入同一消息流。本篇定义消息域（message-svc）的行为、数据与接口；协议信封、游标同步框架以 14 篇为准。

设计基线（00 篇 §2.1）：峰值 5,000 msg/s（2 万用户租户）；普通群 ≤ 500 人、广播群 ≤ 5,000 人（只读）；消息按月分区；漫游默认 180 天。

### 1.2 消息类型全集

| # | 类型 | `type` 值 | 承载方式与说明 |
|---|---|---|---|
| 1 | 文本 | `text` | 受限 Markdown（粗体/斜体/行内代码/链接/列表），≤ 5000 字（超出 3004） |
| 2 | 表情回应 | —（非独立消息） | 挂在目标消息 `ext.reactions`：`{emoji: [uid…]}` 聚合展示，不占 seq，见 §4.4 |
| 3 | 引用 | —（修饰字段） | `reply_to_seq` + 快照摘要，任意类型消息可携带，渲染为气泡顶部引用条 |
| 4 | @提及 | —（修饰字段） | `mentions: [{uid, all, range}]`；`all=true` 即 @全体，受群策略限制（§4.5.4） |
| 5 | 图片 | `image` | body 引用 file 域 `{file_id, w, h, caption}`，caption 为可选随图说明文字（渲染于缩略图下方；OQ-C28 回填）；消息流内先渲染 240 缩略图，点击进查看器（07 篇 §4） |
| 6 | 文件 | `file` | body `{file_id, name, size, ext}`；卡片内显示进度与"转存为协作文档"（07 篇 + 06 篇 import） |
| 7 | 语音条 | `audio_clip` | body `{file_id, duration(≤60s), waveform[≤60]}`；客户端录制即转码 opus/aac |
| 8 | 视频卡片 | `video` | body `{file_id, poster_file_id, duration, size}`；卡片点击走下载票据拉流（07 篇） |
| 9 | 文档卡片 | `doc_card` | 引用 doc 域在线文档 `{doc_id, title, format, version, updater_id}`；点击经 WOPI 会话打开（06 篇） |
| 10 | Agent 分享卡片 | `agent_card` | body `{agent_session_id, task_title, summary_md, artifacts[]}`；用户把 Agent 会话产出分享进会话（08/09 篇），查看不离开 IM |
| 11 | 机器人卡片 | `bot_card` | 20 篇 Incoming Webhook 三模板之一；渲染带 BOT 徽标；发送者 user.type=bot，**bot 不计入群人数上限（3010 口径对 bot 豁免）** |
| 12 | 系统消息 | `system` | 服务端生成的事件通知（入群/移出/禁言/公告变更/解散等），居中弱化样式，不参与回执 |
| 13 | 合并转发 | `merge_forward` | body `{title, count, items:[{sender_id, type, digest, origin_conv, origin_seq}]}`；点开子列表逐条按 `origin_conv+origin_seq` 拉快照 |
| 14 | 通话卡片 | `call_card` | 由 05 篇定义，本篇仅登记：通话结束/未接时服务端落流，复用 `system` 渲染框架 |
| 15 | 会议卡片 | `meeting_card` | 21 篇：预约会议入群卡片（时间/议程/RSVP/入会按钮），会前提醒更新状态；配套会话类型 `meeting_chat`（会中临时聊天） |
| 16 | 邮件卡片 | `mail_card` | 22 篇：邮件转发到 IM 的卡片（主题/摘要/附件可转存文件域） |

### 1.3 非目标

端到端加密（15 篇延后项）、消息翻译、跨企业互联、>5,000 人超大群（见 §9 开放问题）。

## 2. 角色与场景

## 4. 核心交互流程

### 4.1 消息生命周期（本地状态机 + 服务端 seq）

```
本地（每端独立）                                    服务端
┌───────────┐ 发送:先落SQLite再上送
│ composing │ ────────────────────────┐
└───────────┘ (仅输入框态,不落库)        ▼
                              ┌──────────────┐
              ┌──────────────►│   sending    │ 本地outbox队列
              │   重试(自动×3/ │  (已落库)     │
              │    用户点重试)  └──┬────────┬──┘
              │                  ack(seq)│ 10s无ack / code≠0
              │                      ▼    ▼
              │                 ┌──────┐ ┌────────┐
              │                 │ sent │ │ failed │──用户删除──► 从outbox移除
              │                 └──┬───┘ └────────┘
              │          撤回(≤窗口)│ │编辑(≤5min,仅text)
              │                    ▼ ▼
              │              ┌──────────┐   msg.recall/msg.updated 推全端
              └──(重发复用)───│recalled/ │──► 服务端: status 2=recalled 3=edited
                             │edited    │   占位消息保留,seq 不断裂
                             └──────────┘
```

发送时序（02 篇 §4.2 细化）：

```
A端(任一设备)        message-svc                     B端各设备(在线)         离线B
   │ msg.send{client_msg_id, conv, type, body} │                        │
   │───────────────────►│ ①成员/权限校验(3001)     │                     │
   │                    │ ②敏感词策略(3005,§7.3)    │                     │
   │                    │ ③限频(3007)·内容上限(3004) │                     │
   │                    │ ④Redis INCR 分配 seq      │                     │
   │                    │ ⑤落库(message,按月分区)    │                     │
   │   ack{seq, ts}     │ ⑥更新conv冗余+未读索引     │                     │
   │◄───────────────────│ ⑦Redis fanout────────────►│ msg.new × N端       │
   │  SQLite: sent      │ ⑧广播群:跳过⑦,仅更新latest_seq(§7.4)            │
   │                    │ ⑨B离线: 留sync补拉,不逐条推 ──────────────────► (重连后 GET /sync)
```

- **幂等**：`client_msg_id`（客户端 UUID）+ UK `(conv_id, client_msg_id)`；重试/重放返回原 seq 不重复落库（14 篇 §5.3）。
- **seq 分配**：Redis `INCR t:{tid}:conv:{cid}:seq`；message-svc 重启时以分区表 `max(seq)+1` 对齐，防止 Redis 丢失回退。
- 本端发送中的消息以临时序（`t-1`）渲染于列表底部，收到 ack 后按真实 seq 归位。

### 4.2 送达与已读回执

| 机制 | 触发 | 存储 | 展示 |
|---|---|---|---|
| 已送达 | 服务端成功投递至对端任一设备（gateway 推送成功即近似送达） | message_receipt.delivered_seq | 单聊 ✓（单勾） |
| 已读 | 端侧进入会话且消息进入可视区 → `msg.read{conv_id, read_seq}`（连续最大 seq） | message_receipt.read_seq | 单聊 ✓✓（双勾） |
| 群已读 | 同上，聚合为已读人数 | 同上（O(成员数) 而非 O(消息数)） | "已读 N/M"，点开查看名单（见下） |

策略：**单聊默认开；群聊由租户策略 `im.read_receipt` 控制，默认关**（开时默认仅群主/管理员可见名单，租户可放开全员）。已读游标变更经 `msg.receipt`（本篇新增，§6.2）推送对端。回执只推进不回退；多端取各端已上报的最大值为准。

### 4.3 撤回与编辑

| 项 | 撤回 | 编辑 |
|---|---|---|
| 窗口 | 默认 **24h**，租户可配 5min–7d（12 篇合规策略） | **5min**（固定，防历史被改写） |
| 范围 | 本人消息；管理员持 `im:message:recall_any` 可撤他人（合规处置） | 仅本人 `text` 消息 |
| 协议 | `POST /api/v1/messages/{id}/recall` | `PATCH /api/v1/messages/{id}` |
| 推送 | `msg.recall` → 全端替换为"张三 撤回了一条消息"占位 | `msg.updated` → 原地更新 + "已编辑"角标 |
| 保留 | 占位消息保留（seq 不断裂）；原内容移入审计留痕（audit 域，15 篇） | `edit_history` JSONB 保留全部历史版本 |
| 超窗 | 3003 | 3008 |
| 联动 | 撤回文件类消息仅失效卡片，file 对象保留在发送者"我的文件"（07 篇） | 编辑不触发重新推送通知/未读 |

### 4.4 表情回应

1. 用户在消息上长按/右键 → 回应面板（常用 emoji + 更多）。
2. `msg.reaction.set{msg_id, emoji, action: add|remove}`（本篇新增 WS 事件）。
3. 服务端更新 `message.ext.reactions`（Redis 缓存 + 异步落库），同一用户同一 emoji 幂等，可对同一消息给多个不同 emoji。
4. 广播 `msg.reaction.new{msg_id, reactions}` → 各端增量合并；回应条渲染在气泡底部（`😊×3`，悬浮看名单）。
5. 回应不占 seq、不计未读、不触发系统通知。

### 4.5 群聊设计

#### 4.5.1 角色权限矩阵

| 操作 \ 角色 | owner | admin | member | 广播群 publisher |
|---|---|---|---|---|
| 修改群名/头像 | ✓ | ✓ | ✗（群设置可放开） | ✗ |
| 发布/修改群公告 | ✓ | ✓ | ✗ | ✓（公告即内容） |
| 邀请成员 | ✓ | ✓ | 按 `invite_policy`（all/admin，默认 all） | ✗ |
| 审批入群申请 | ✓ | ✓ | ✗ | ✗（广播群无审批，管理员直接加） |
| 移出成员 | ✓ | 仅 member 级 | ✗ | ✗ |
| 单人禁言 | ✓ | ✓（不能禁 owner/admin） | ✗ | ✗ |
| 全员禁言 | ✓ | ✓ | ✗ | —（本就只读） |
| @全体 | ✓ | ✓ | 按 `mention_all_policy`（all/admin/none，默认 admin） | ✓ |
| 设置/撤销管理员 | ✓ | ✗ | ✗ | — |
| 转让群主 | ✓ | ✗ | ✗ | — |
| 解散群 | ✓（广播群亦可由租户管理员） | ✗ | ✗ | ✗ |
| 退群 | 需先转让或解散 | ✓ | ✓ | — |
| 发消息 | ✓ | ✓ | ✓（未禁言） | ✓（广播群唯一可发言角色） |

#### 4.5.2 群生命周期流程

| 流程 | 编号步骤 |
|---|---|
| 建群 | ① 选成员（≤499，建群者即 owner）→ ② `conv.create{name, member_ids, type}` → ③ 服务端建 conversation + member 批量落库 + 系统消息"张三 创建了群聊" → ④ 各端 `conv.updated` + 会话入列表 |
| 邀请 | ① 邀请人选择用户 → ② `conv.member.add{uids}` → ③ 校验 invite_policy/人数上限（3010）→ ④ 被邀端系统消息 + 会话入列表（`join_mode=direct` 直接入；`apply` 模式转为向其发申请确认） |
| 审批入群 | ① 用户搜索/扫码找到群 → ② `conv.apply{reason}` → ③ 群主/管理员收通知（会话内系统消息 + 通知中心）→ ④ `conv.apply.handle{apply_id, approve|reject}` → ⑤ 通过则入群并广播系统消息；申请 7 天未处理自动过期 |
| 退群 | ① `conv.quit` → ② 校验非 owner（3016）→ ③ 移除 member + 系统消息 → ④ 该端清会话入口（历史按 `history_visible` 决定是否可再查看） |
| 移出 | ① 管理员在成员列表操作 → ② `conv.member.remove{uid}`（矩阵校验，3015 无权/3011 目标非法）→ ③ 被移出端 `conv.updated` + 强制退出会话视图 + 系统消息 |
| 解散 | ① `conv.dissolve`（仅 owner/租户管理员）→ ② status=dissolved → ③ 全端 `conv.updated(status)` + 会话标记"已解散"只读 → ④ 二次确认弹窗；全程审计 |

#### 4.5.3 群公告与禁言

- 公告：`conv.setting{announcement}` → 全端 `conv.updated` + 系统消息 + 消息流顶部置顶横幅（可关闭，红点提示更新）；公告历史保留在详情侧栏。
- 单人禁言：`mute_until`（≤30 天/次），被禁者发送返回 3006，UI 显示禁言剩余时长。
- 全员禁言：`mute_all_until`，例外名单（群主/管理员恒可发言）；系统消息告知全员。

#### 4.5.4 两档群型

| 维度 | 普通群 group | 广播群 broadcast |
|---|---|---|
| 人数 | ≤ 500（3010） | ≤ 5,000（3010） |
| 发言 | 全员（角色+禁言约束） | **只读**，仅 publisher（`im:broadcast:publish`） |
| 扇出 | 写扩散（§7.4） | 读扩散（§7.4） |
| @/回应 | 支持（@全体受策略） | 不支持 @；支持表情回应（本地态，不广播全名单） |
| 建群权限 | `im:group:create` | `im:group:create_broadcast`（默认仅租户/部门管理员） |
| 典型用途 | 部门群、项目群 | 全员公告、政策宣贯 |

### 4.6 多端同步

游标模型与登录/重连同步流程沿用 14 篇 §4（per-conv seq 游标、GET /sync 增量、gap 提示翻页），本篇补充：

| 项 | 约定 |
|---|---|
| 游标粒度 | 每用户每会话每端独立（服务端按 user 汇聚 `read_seq`，端内按设备记 `acked_seq`） |
| 漫游 | 服务端保留默认 180 天（租户 30–3650，16 篇分区归档策略一致）；更早消息只读走归档查询（管理侧合规检索） |
| 广播群优化 | `/sync` 响应中广播群仅返回 `{conv, latest_seq, unread}` 不带消息体，进入会话时按游标分页拉取 |
| 会话内补洞 | 检测 seq 不连续（收到 seq=131 但本地 max=129）→ `GET /convs/{id}/messages?after=129&before=131` 精确补拉，期间新消息正常入列 |
| 本地 SQLite 缓存 | 见 §5.2；写入顺序：**先落库再渲染**（崩溃可恢复） |

### 4.7 搜索（两级）

| 层级 | 引擎 | 范围 | 触发 |
|---|---|---|---|
| L1 本地 | SQLite FTS5（unicode61 + trigram，中文子串可用） | 本端已缓存消息 | 输入即搜，<50ms，无网络可用 |
| L2 服务端 | PG FTS（zhparser 分词，GIN 索引） | 漫游期内全量消息 | 本地无结果/用户点"全网搜索"自动升级 |

- 过滤器：`keyword`（必填）、`from_uid`（按人）、`conv_id`（按会话）、`type`（按类型：文件/图片/链接/语音…）、`from_ts/to_ts`（时间段）；组合 AND。
- 结果条目：命中片段高亮 + 会话名 + 发送人 + 日期；点击跳转 → 拉取目标 seq 前后各 20 条并滚动定位、闪烁标记。
- 入口：会话列表顶部搜索框（全局）；详情侧栏"在会话内搜索"（预置 conv_id 过滤）。

### 4.8 通知与红点

| 项 | 规则 |
|---|---|
| 触发条件 | 窗口最小化/失焦，或消息不属于当前打开会话时发系统通知（Tauri 通知，托盘协作） |
| 聚合 | 同一会话 10s 窗口内合并：`【产品研发群】张三： xxx ×3`；同租户 1 分钟内 ≤5 条系统通知，超出仅计红点 |
| 勿扰层级 | 会话级 mute（列表 🔇）> 用户级 `pres.set` 勿扰（含免打扰时段）> 系统专注助手 |
| @优先 | `@我` 与 `@全体`（在 mention_all_policy 允许时）**穿透会话勿扰**（租户策略可关闭穿透）；广播群新发布穿透用户勿扰（默认开） |
| 红点 | 主导航徽标 =Σ未读会话数（99+）；托盘角标同源；免打扰会话计小圆点不计数字；@未读在会话徽标加 @ 角标 |
| 点击路由 | 通知点击 → 激活窗口 → 打开对应会话并定位到触发消息 seq |

## 7. 边界/异常/降级

### 7.1 弱网重发

outbox 队列：WS 重连成功后按序重发 sending 态消息（幂等保证不重复）；10s 未 ack 重试 ≤3 次（指数退避）→ failed + UI 重试按钮；failed 消息长按可删除或复制内容重发。离线期间正常浏览本地缓存与撰写草稿。

### 7.2 顺序保证

- 渲染顺序一律以 seq 为准（14 篇 §4.3）；本地 sending 消息临时序置底。
- seq 空洞：不阻塞渲染，后台补洞（§4.6）；补洞失败 3 次提示"消息加载异常，点击重试"。
- 跨端时钟偏差不影响正确性（客户端 ts 仅展示参考）。
- 同会话并发写：seq 由 Redis 单点分配，天然全序；同 client_msg_id 并发到达以 UK 冲突回退返回首个结果。

### 7.3 敏感词策略（租户三模式，可按会话类型叠加）

| 模式 | 行为 | 端侧表现 |
|---|---|---|
| 拦截 block | 拒绝落库，返回 3005 | 消息进 failed 态，提示"包含违禁词"（不回显命中词） |
| 替换 mask | 命中词替换为 `**` 后正常落库 | 正常发送，展示已替换内容 |
| 审计 audit | 原文放行 + 异步写 audit 事件 | 无感知 |

词库由租户管理后台维护（12 篇），message-svc 内存缓存 + 变更推送热更；命中记录（词、会话、发送者、模式）写 audit 域（15 篇），不在消息体留痕。

### 7.4 扇出选型：普通群写扩散、广播群读扩散

| 维度 | 普通群（≤500）写扩散 | 广播群（≤5000）读扩散 |
|---|---|---|
| 存储 | 消息落会话 timeline 一份；**另写每成员未读索引/摘要冗余**（user_conv_state，异步批量，100ms 窗口聚合落库） | 消息仅落会话 timeline，不写成员级冗余 |
| 在线推送 | Redis fanout → 各端 gateway `msg.new` | 跳过逐端 msg.new，仅更新 latest_seq；在线端凭 `badge.updated` 感知，**进入会话时按游标拉取** |
| 写放大 | ≤500/条（峰值预算：5,000 msg/s × 平均扇出系数 ≤20，大群消息占比受 §4.5 限频约束） | ≈0 |
| 未读 | unread_badge 冗余计数 | `latest_seq − read_seq` 差值实时计算 |
| sync | 带消息体增量 | 仅 `{latest_seq, unread}` + gap 提示 |
| 理由 | ≤500 规模写放大可控，换取列表/未读/推送的低延迟读路径 | 5,000 人逐端写不可接受；只读场景读延迟可被"进入会话才拉"吸收 |

降级开关：普通群规模监控异常（fanout 积压 > 10s）时，运维可对该租户 >1,000 人的普通群临时切读扩散路径（feature flag，14 篇灰度机制）。

### 7.5 其他边界

| 场景 | 处理 |
|---|---|
| 消息体上限 | text ≤5000 字；图片/文件/视频消息 body 仅存 file 引用不存二进制（大流量走 07 篇预签名直传） |
| 限频 | 单用户 10 msg/s、单会话写入 50 msg/s（超出 3007）；@全体 每人每群 5 次/10min |
| 漫游到期 | 游标早于保留期起点 → sync 返回 gap+fetch_url 翻页；归档分区只读（16 篇） |
| 单聊对方离职 | user status=disabled（03 篇 §4.5）：会话保留可读，发送返回 2xxx 用户禁用；会话列表弱化标记 |
| 群成员 500 上限 | 邀请批量操作前预检余量，不足则部分成功+失败明细返回（3010 逐个标注） |
| 合并转发嵌套 | 转发 merge_forward 消息时展开为原始条目重组，嵌套 ≤3 层（3021） |
| message-svc 过载 | 降级序：L2 搜索限流 → 回执合并上报（60s 粒度）→ typing 停发；消息收发为最后降级项 |

## 9. 开放问题

1. 群已读回执开启后的性能路径：>200 人群是否限制"仅显示已读数、不可展开名单"。
2. 消息收藏是否需要分类文件夹（当前平铺 + 搜索）。
3. >5,000 人场景（全员大会直播式通告）是否引入"频道"模型（只读 + 万人级），与广播群合并或并存。
4. 输入状态（typing）在群聊是否默认关闭以降低噪声与流量。
5. 单聊是否提供"消息免回执"细粒度开关（与租户审计要求的冲突需 15 篇评估）。
